#+title: dorg Development Guide

This file is the durable architecture and development ledger for DOrg.  It is
not a task tracker: current work and its evidence live in the project's issue
tracker, not here.  Keep this file for source-backed design facts, module/test
maps, contributor commands, and long-lived decisions that should survive
outside an issue.

* Emacs support scope

GNU Emacs 30.1 is the supported CI target.  Emacs 29 is unsupported and
unverified following the test-runner skip-handling failure documented in
[[file:README.org::*Emacs 29 compatibility][Emacs 29 compatibility]].  Excluding a version from CI is not evidence of
a runtime incompatibility.  The existing package metadata minimum is
retained; it does not certify compatibility with every permitted version.

* Architecture

DOrg stores Org-shaped documents in either plain Org buffers or Dolt-backed
relational storage.  A Dolt-backed Org buffer is a read-only projection: users
read, navigate, query, and refresh it like Org, but writes enter through the
typed command/mutation door.  This boundary is implemented by
[[file:dorg-api.el][dorg-api.el]], [[file:dorg-command.el][dorg-command.el]],
[[file:dorg-app.el][dorg-app.el]], [[file:dorg-mutate.el][dorg-mutate.el]],
[[file:dorg-mode.el][dorg-mode.el]], and the storage modules listed in
[[*Modules][Modules]].

** Local file gate owner identity

Saved plain-Org writes and Git maintenance share the atomic symlink owner
protocol in [[file:dorg-file-lock.el][dorg-file-lock.el]].  Linux uses
the kernel boot ID, PID namespace and raw start ticks from procfs; Emacs's
derived wall-clock start can vary between observations of one live process.
Darwin retains validated, semantically compared process start times.  Only
affirmative death in the recorded scope permits reclamation; malformed,
unreadable, foreign-host or incompatible identities preserve the lock.

Legacy untagged maintenance owner records also remain preserved, including
stale records after a crash.  They are not silently converted or automatically removed.
Recovery requires separately authorized verification that the owner is dead;
this change provides no cleanup command.  New owner records are published in
one symlink creation, so a killed writer leaves either no lock or a complete
record.  Token release and fixed tombstone election protect successor locks.

** Managed clock authority

The =DORG_CLOCK_= owner keeps interval identity, exact UTC seconds and the
one-active pointer in one Dolt root.  An immutable owner intent enters the
same API gate, mutation planner and operation receipt as other typed writes.
Its request digest includes expected-active but excludes the first-apply base;
the owner validates state at the planner's frozen base.  CLOCK text is a
minute-resolution projection and cannot identify an interval.  Plain files
may be task references, but a plain-only clock authority has no durable replay
contract and refuses lifecycle writes.

The closed owner registry in [[file:dorg-model.el][dorg-model.el]] resolves a
participant by loading its declared feature at each API, mutation, restore
and import boundary.  The clock participant and public API keep Dolt modules
unloaded until a Dolt read or write is requested.  The explicit store
identification door delegates its gate-held =dorg_meta= write to
[[file:dorg-repo.el][dorg-repo.el]], which owns store identity and SQL.

** Write Path

Extension owner partitions resolve changed-heading membership once against
the immutable base and candidate images.  Their side-qualified affected paths
drive the owner-local overlays through an entry-id index.  Overlaying must not
re-resolve unrelated owners against a partial partition: sibling normalization
can affect many owners, making that approach quadratic in database reads.

1. A caller — ~dorg-api-execute~, ~dorg-set-property~, =dorg mutate=, or the
   HTTP mutate route — submits a public DSL form or mutation intent.
2. [[file:dorg-api.el][dorg-api.el]] reads and normalizes the request,
   protects identity fields, and lowers it to typed patch IR.
3. [[file:dorg-mutate.el][dorg-mutate.el]] resolves the source, validates the
   typed patches, plans source-generic effects, and simulates the candidate
   image.
4. The store gate and transaction open: ~dorg-mutate-call-with-store-gate~,
   the SQL session lease, and ~dorg-transaction-commit~ where administrative
   import needs an exact base.
5. Pre-commit validation runs HEAD/base checks, structural consistency,
   extension index candidate validation, and postimage expectations.
6. Commit and receipt: ~dorg-sql-batch~ / ~dorg-commit~, the mutation log and
   compact operation identity/generation/intent fingerprint, and the response envelope.
7. Derived readers refresh: materialized projections at the exact token,
   extension read-cache invalidation, and warm session freshness on the next
   read.

Retired boundaries are not supported alternatives.  Whole-file
edit/parse/diff/three-way reconciliation, save-hook write-back, dirty-buffer
promotion, and reconciliation conflict production are removed.  The current
write contract is the typed mutation path documented in
[[file:docs/mutate.org][docs/mutate.org]].
Parallel expectation checking has been replaced by candidate/postimage
validation in the single write path.

** Consumer Boundary

*** Query column selection

A query may finish with ~(select EXPR...)~. Field and property expressions
choose returned columns; ~(as EXPR NAME)~ names a column. The adapters keep
heading identity separately from selected values, so result navigation does
not depend on an optional display column. Mutation target expansion refuses
queries with a ~select~ step; targets are heading selections.

The parser and model/plain/Dolt adapters share this plan. SQL projection
avoids fetching all properties: title-only results require no property read,
and selected properties are fetched for the selected IDs and keys at the same
captured revision. Warm-session serialization retains selected values while
removing live markers. The query architecture preserves one shared plan
across library, CLI, and downstream consumers.

*** Public application surface

A downstream application reaches typed mutation, query, materialization,
import, and server lifecycle exclusively through the public surface.
Supported calls:

- ~dorg-api-execute~
- ~dorg-command-run-query~
- ~dorg-ql-select~
- ~dorg-ql-select-snapshot~ / ~dorg-ql-snapshot-public~
- ~make-dorg-registration~, ~dorg-backend-dolt~ and ~dorg-repo-root-id~
  for an ephemeral query binding to an existing Dolt root; see the
  [[file:docs/api.org::#query-library-api][query source contract]]
- ~dorg-materialize~ / ~dorg-refresh-materialized-view~
- ~dorg-register-extension~ and documented extension callbacks

Forbidden above the door:

- raw SQL as an application write API
- byte-splicing Dolt-backed projections
- save-hook whole-file reconciliation
- private =dorg-*--= helpers as compatibility API

** Server And Transport Topology

- Interactive ~dorg-mode~ :: ~dorg-dolt-auto-server~ starts the
  [[file:dorg-dolt-server.el][dorg-dolt-server.el]] detached managed daemon,
  which publishes a claim file in the store; clients then speak strict
  =mysql.el= transport through [[file:dorg-transport.el][dorg-transport.el]].
- CLI / batch command :: attaches to a compatible visible managed server;
  otherwise it fails by default with an explicit start remedy.  Optional
  ~dorg-dolt-server-autostart~ starts the same detached daemon.
- One-shot SQL fallback :: internal recovery seam only; it sits outside
  DOrg's managed-server health and target-selection guarantees.
- Test/runtime isolation :: DOrg-owned scratch roots live under the test
  runtime with store-local claims and indexes; cleanup may remove only owned,
  exact, canonicalized paths.

  end

The authoritative lifecycle code is in
[[file:dorg-dolt-server.el][dorg-dolt-server.el]].  Transport policy is split
into [[file:dorg-transport.el][dorg-transport.el]] and the SQL/lease
implementation in [[file:dorg-dolt.el][dorg-dolt.el]] so callers do not select
an unmanaged path accidentally.

- Programmatic writes: ~dorg-api-execute~ in [[file:dorg-api.el][dorg-api.el]].
- Programmatic reads: ~dorg-ql-select~ in [[file:dorg-ql.el][dorg-ql.el]] and

  =doctor=, =serve start|stop|status=, and
  =dolt list|status|start|stop|stop-all|compact|rebind= through

  [[file:dorg-import.el][dorg-import.el]].
- Extension registration and derived indexes: ~dorg-register-extension~ and
  related documented accessors in [[file:dorg-ext.el][dorg-ext.el]] /

* Build And Test Commands

Query/API test fixtures build committed core data directly with
~dorg-test-ql--seed-document~.  Every case gets a fresh writable database;
setup parses its Org text, inserts the rows, commits once, and constructs the
registration in memory.  It does not run administrative import or binding
validation.  The fixture's parity test compares its committed model with a
real import; the import, schema, and binding suites retain their real lifecycle
paths.  The fixture deliberately rejects registered extensions because it
only seeds the core schema.  The optional timing profiler reports this setup
as the ~seed~ phase.  Its file-binding row is built directly from the owned
store and document paths, whose casing is already known.  Ordinary fixtures
do not pay for production binding's directory scans to discover that casing;
the real import/binding contracts continue to verify path normalization.

Automated Linux jobs use an init reaper and an unprivileged UID so detached
process cleanup and permission assertions exercise normal user behavior.
The common launcher passes Docker's =--init=; its exact runtime-managed
=/sbin/docker-init= mount (=/usr/sbin/docker-init= on a merged-/usr image)
is allowed alongside the standard Docker mounts.
The only caller-supplied bind remains =/artifacts=.
The suite image pins Git 2.49.0 and records the observed version before the
gate; Debian Bookworm's Git 2.39 includes extra packed objects in two
maintenance fixture scenarios. Toolchain sources and checksums live in
[[file:.github/dorg-suite-job/image-lock.org][the image lock]].
The shared local and Actions suite launcher runs its container with Docker
=--network none=. Its external-egress allowlist is empty: suite tests use
loopback fixtures, including Dolt. Image construction downloads pinned inputs
before this isolated container starts. Before admitting source bytes, the
entrypoint probes the actual namespace for non-loopback interfaces, IPv4 and
IPv6 routes, and bounded outbound attempts in both families. Only immediate
network-unreachable results pass. The manifest records the observed mode and
probe results alongside the launcher expectation; a mismatch fails the gate.
On GNU/Linux, store-claim recognition decodes Emacs's escaped process arguments
before comparing an explicit data directory; Darwin retains its display parser.

The existing CI workflow accepts an optional =selector= on manual dispatch.
It passes the regexp to the same suite job's =--selector= mode, which records
=gating=false=. Use this for focused remote diagnosis; release certification
still requires the full job with no selector. Push and pull-request jobs
continue to run the full suite.

All DOrg gate and trunk pushes, and all manual gate dispatch, status and
artifact-download operations, go through [[file:tools/dorg-private-venue][=tools/dorg-private-venue=]].
Its =push-gate CODE SHA= command derives a candidate-unique =ci/CODE-SHA12=
ref; =push-trunk SHA= publishes an exact merge commit. The command resolves
the private GitHub push URL after Git rewrites, refuses ambiguous or different
destinations, and reads back the pushed ref. =dispatch CODE SHA=, =list CODE
SHA=, =view RUN_ID= and =download RUN_ID DIR= pin the same private repository
for every GitHub CLI call. Raw =git push= and unqualified =gh workflow/run=
commands bypass that venue check and are outside the DOrg gate process.
The workflow job also checks its repository before starting, while the
container records and verifies the Actions repository and server URL in its
manifest. A skipped public job is not a certification receipt.

The same job can admit a source packet for a consumer with private dependencies:
=tools/dorg-suite-job-local --source-packet FILE --commit SHA --tree TREE=.
Its source manifest names the exact root and complete recursive gitlink set;
the importer validates standard Git bundles before any make command. The
workflow/tooling revision remains separate from the candidate being certified.
The existing compile/lint/full commands, isolation and result classifier still
own execution. Packet transport needs no cross-repository credential or mutable
submodule fetch. =tests/test_suite_source_packet.py= exercises real small Git
fixtures through =dorg-test-job-source-packet-real-git-controls=; Python is an
explicit image prerequisite. Platform and missing-consumer capability skips
must be reported separately from executed tests.

The host launcher keeps custody of its container when it is interrupted. It
requires GNU =timeout= (and refuses before writing anything without it), gives
=docker run= a run-private =--cidfile= and a unique =dorg-suite-job.run= label,
and runs the export/Docker pipeline as a background job in its own process
group so that HUP, INT and TERM are handled while Docker runs; a foreground
pipeline would defer the traps until the container exits. A signal that
arrives while the job is being started is held until its process group is
recorded; once the outcome is fully written the launcher ignores further
signals and exits with it. On any interruption
or abnormal exit one handler ends only that job group, then stops and removes
the container only when the full ID in the cidfile and the run label both
verify, with every Docker call bounded. A missing or unverifiable identity is
recorded in =host-census/cleanup.txt= and never guessed: a container created
before its cidfile was written stays reported as residue. The interruption is a
missing fact in the existing verdict, so the run is =incomplete= with its
128+signal status even when the container had already written a green receipt,
whose fields are retained. SIGKILL of the launcher and CI workflow cancellation
are outside this contract and belong to the external job owner.
=tests/test_suite_job_cancellation.py= drives the real launcher against a fake
Docker client through =dorg-test-job-launcher-cancellation-controls=.

** Derived pre-ACCEPT families

=make test-derived BASE=<rev> [OUT=<dir>] [DRY=1]= runs the whole test files a
candidate (the clean checkout's HEAD) must pass, derived from its changes
against =merge-base(BASE, HEAD)=.  [[file:tools/dorg-derive-families.el][=tools/dorg-derive-families.el=]] owns the
rules; [[file:tests/dorg-derive-families-tests.el][its specs]] pin each one in both directions.

The derivation reads git objects only: =diff -z --name-status -M= records
(copy detection refused), changed line ranges, blobs and the candidate's
=tests/= tree.  A test file is selected by any of:
- R1, a changed test: added, modified or type-changed, or a renamed test's
  new path.  A deleted test never is.
- R2, a module: =tests/M-tests.el= and =tests/M-*-tests.el= for a changed root
  module =M.el=, under its old and new names.
- R3, a definition: the definitions /containing/ each changed line, found
  syntactically in the old and new text.  Git's .el hunk headers name
  docstrings, not definitions.  A test is selected when it references one as a
  whole symbol.
- R4, a helper: a changed =tests/= support file selects the tests that
  require its features or load it by name.  A =tests/fixtures/DIR/= change
  selects the tests naming that directory.
- R5, a path: any changed non-test path that is not a root module selects the
  tests naming it verbatim.
- R6, the census: every test that enumerates the repository runs whole when
  its trigger class fires.  The classes are root modules, =tests/*.el=,
  =tests/**=, =tools/**/*.el=, =lib/=, =docs/=, the build surface, the
  shipped file set, and any change.  The table and its reasoned exemptions
  live in the tool, and a guard spec fails on any new undeclared enumerator.
- R7, behaviour families: the lock, maintenance and plain-writer modules
  select the infrastructure and persistence tests, and a module touching
  =kill-emacs-hook= selects the infrastructure tests.

The tool counts the selected tests in a child that loads the real runner,
attributing each test by its defining file.  It then runs them in a second
child through =dorg-run-tests--batch=, which keeps its own teardown and exit
status.  HEAD, tree and cleanliness are rechecked before and after the run.
The executed names must equal the counted names per file.

The receipt in =OUT= holds:
- =identity.txt= and =phase.txt=;
- =derived.eld= (files and the reasons each was selected);
- =counts.eld= and =selector.el=;
- =census-before.txt= and =census-after.txt= (pid, ppid and basename of dolt
  and emacs processes only, never command lines);
- =run.log= and =result.txt=.

Exit codes:
- 0 pass or dry run;
- 2 empty derivation;
- 3 a selected file with no loaded test, i.e. unregistered;
- 4 identity: BASE, merge-base, dirty tree or drift;
- 5 a git, read or parse failure, or stale tool bytecode;
- 6 a missing summary, or an executed set that differs from the counted one;
- otherwise the runner's own failing status.
No path falls back to a default or full selection.

* Code Style

- Use =lexical-binding: t= in Emacs Lisp files.
- Prefix public symbols with ~dorg-~ and private implementation helpers with a
  double-hyphen namespace such as ~dorg-mutate--~.
- Keep public functions documented with docstrings.
- Prefer source-generic APIs at boundaries; storage-specific helpers stay below
  their adapter.
- Treat Dolt-backed Org buffers and =/dorg:= views as read-only projections.
  Add a typed command when a write workflow is missing.
- Keep generated artifacts generated.  In this tree,
  [[file:docs/generated/mutate-grammar.org][docs/generated/mutate-grammar.org]]
  is produced by =make mutate-grammar=.

* Adding A Module

1. Add the root module file and provide feature.
2. Add a direct or transitive require where the module belongs.
3. If the module defines structs or macros, update ~dorg--reload-priority~ in
   [[file:dorg.el][dorg.el]].
4. Add or update tests under =tests/= and require them from
   [[file:tests/dorg-tests-runner.el][tests/dorg-tests-runner.el]].
5. Update the [[*Modules][Modules]] and [[*Tests][Tests]] example blocks in this
   file.
6. Run the focused tests for the changed area and
   =make test SELECT='^dorg-test-project-'= when maps or public docs changed.

* History

** Machine-First Reset

The 2026-07-24 machine-first reset stopped treating whole-file three-way
write-back as the release path.  Subsequent landings removed reconciliation
modules and conflict-runtime support; the surviving architecture is
DB-as-truth storage plus read-only projections and typed mutation.

** Deep-DOrg Ratification

The August 2026 mutation and projection work made the single write door
executable: public requests lower to typed patch IR, the engine simulates a
candidate image, validates core and extension postconditions before commit, and
returns structured receipts.  [[file:docs/mutate.org][docs/mutate.org]],
[[file:docs/api.org][docs/api.org]], and
[[file:docs/backend-extension.org][docs/backend-extension.org]] are the public
details; this file records the system shape.
