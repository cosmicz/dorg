#+title: DOrg Configuration

#+begin_quote
*Current DOrg configuration.*  Whole-file save/enable synchronization is
not installed.  Dolt-backed buffers are read-only projections and writes belong
on the typed mutation/command API.
#+end_quote

This document lists the user-facing options and hooks that tune dorg's
projection, server, and id-generation behaviour.  For their runtime roles, see
the relevant module API tables in [[file:api.org][docs/api.org]].

* Runtime installation

=make install= copies DOrg, its launcher, Clime, web-server and mysql.el with
notices into =DORG_HOME= (default =$PREFIX/share/dorg=), compiles there, checks
the staged help/install doctor, then publishes the runtime and launcher link.
With no caller-provided =PREFIX=, =PREFIX= defaults to =$HOME/.local= and
=BINDIR= to =$HOME/bin=.  A caller-provided =PREFIX= keeps =BINDIR= at
=$PREFIX/bin= by default.  =install.sh= clones source into
=$HOME/.local/src/dorg= by default and wraps the same install target.  Keep
bundled =lib/= dependencies intact.

The installer refuses an unmanaged destination or a non-symlink launcher.
The compile Emacs must match the one the launcher resolves.  Failure before
the final link replacement leaves the prior install available; after that
commit point the new install is kept.  Reinstallation replaces the owned
runtime tree.  Extensions loaded as =dorg-extension-NAME= remain on the
caller's =EMACSLOADPATH= rather than being discovered from a checkout.

* Default project store convention

New project integrations use =<project>/.dorg/dorg/= as the canonical local
DOrg store.  The outer =.dorg/= directory is the project-level DOrg namespace;
the inner =dorg/= directory is the Dolt repository and therefore the database
name exposed by that project's managed server.  Compute this path with
~dorg-default-store-directory~ by passing an explicit absolute project root.
The helper is pure: it neither creates nor discovers a store and does not bind
a source.

The database name is not independently configurable.  DOrg derives it from
the physical store basename, keeping the repository path, server target,
claims, revision-qualified SQL, and connection identity aligned.  Explicit
legacy and custom stores remain valid unchanged: for example, an explicitly
bound =<project>/.tracker/dolt/= store continues to serve database =dolt=.
There is no fallback search, alias, automatic move, or silent re-import.

For a downstream tracker projection at =<project>/.tracker/beads.org=, the source binding
to the canonical store is =../.dorg/dorg=, and the store-relative source
locator is =../../.tracker/beads.org=.  A root-level
=<project>/beads.org= source instead has locator =../../beads.org=.  Moving the
whole project preserves both relative relationships.

External Dolt repository synchronization is orthogonal to the local database
name.  Each project may keep the same local ~dorg~ name while its remote URL
or repository namespace supplies global multi-project identity.  This does
not claim that multiple local stores can be attached directly to one shared
SQL server under the same name; that future topology requires a separate,
durable unique store identity.

* Interactive Dolt projection safety

Any Org buffer carrying a genuine preamble
=#+DORG_DOLT_DIR:= (or legacy =#+DORG_DIR:=) binding is read-only.  The guard
is installed on =org-mode-hook= and re-applied to already-open buffers by
~dorg-reload~, so it does not depend on =global-dorg-mode= or the transient
~dorg-mode~ bit.  DOrg-owned mutations bind =inhibit-read-only= through the
central programmatic-change guard.  Plain-org buffers retain ordinary Emacs
editing and saving.  Batch execution does not bypass a Dolt projection's
identity-derived policy.

* Managing sql-servers

DOrg runs a =dolt sql-server= per Dolt repo to speed up queries from
long-lived interactive sessions.  Servers DOrg starts publish a
same-host /ownership claim/ under the store-relative =<store>/.dorg/=
overlay so other DOrg processes attach to an existing server rather
than starting a second one or contending on the Dolt write lock.

Discoverable commands let you inspect and manage these without
evaluating Lisp (see [[file:api.org][docs/api.org]] for return values):

- =M-x dorg-dolt-list= — show owned servers, attached ports, and
  same-host claims, each classified live / dead / stale / unreachable /
  incompatible.  External non-DOrg =dolt sql-server= processes are not
  shown.
- =M-x dorg-dolt-start= — ensure a server for the current buffer's
  registered Dolt repo (or a prompted directory).
- =M-x dorg-dolt-stop= — owner-safe: stops a server this Emacs owns,
  detaches an attach-only client, or refuses to stop one owned by
  another DOrg process (reporting its pid/port).
- =M-x dorg-dolt-stop-all= — stop every server this Emacs owns.

Starting a server with these commands is an explicit action.  Ordinary
SQL uses strict managed-server transport.

Before DOrg starts a managed server it performs a store-scoped owner census:
it uses =lsof= on the exact =<store>/.dolt/noms/LOCK= and confirms that any
holder is a live =dolt sql-server= for that canonical store.  This is a hard
start prerequisite.  An absent LOCK in a fresh store is clear; a missing or
failed =lsof= probe, malformed process evidence, or an ambiguous holder refuses
the start rather than risking a second server.  Scrubbed environments must keep
=/usr/sbin= available so the system =lsof= remains reachable.

A server's own output — Dolt's log, including every failed statement it
reports — goes to =<store>/.dorg/server.log=, whether this Emacs spawned
the server or it runs as a detached daemon.  The file is truncated each
time a server starts and is not size-bounded while that server runs.  An
Emacs-spawned server never writes to an Emacs buffer, so a burst of logged
errors cannot block it while a query waits for its reply.

~dorg-serve-runtime-dir~ is separate from the Dolt store-relative
=<store>/.dorg/= overlay: it holds the per-port state and token files
for the optional ~dorg serve~ HTTP daemon (not the =dolt sql-server=).
Its contents are volatile and safe to delete when no serve daemon is
running.

* SQL transport (Dolt backend)

For Dolt-backed repos, ~dorg-sql-transport~ is a special policy cell
that selects how SQL reaches Dolt.  It is intentionally not a Customize
option; sessions and workers may let-bind it while the global default
stays strict =server=.  It applies to all post-init SQL (queries,
schema, migration, model load, commit, rollback, and HEAD/root metadata
reads); the =dolt version= and initial =dolt init= calls are exempt.

The packaged default is strict =server= in both interactive Emacs and
noninteractive batch processes (the =bin/dorg= CLI, =make test=).

- =server= — strict server mode: every SQL
  operation routes through a DOrg-managed server (reusing a server this
  process owns, a previously attached port, or attaching to a live
  same-host server that owns the repo) or errors; it never falls back to
  CLI.  On a =server= path, =mysql.el= being unavailable is a
  packaging/configuration error (install the bundled MySQL client
  support), not a silent downgrade.
One-shot CLI is not a public transport setting; it remains only as an
internal test/recovery seam for standalone stores that no managed server
owns.

When no usable server is visible, whether that SQL call implicitly starts
one is governed by ~dorg-dolt-server-autostart~ (default =nil=):

- disabled (the default) — signals ~dorg-sql-transport-error~ naming the
  two remedies, before starting a process or writing any claim/
  =sql-server.info= metadata: run ~dorg dolt start PATH~ (=M-x
  dorg-dolt-start=), or enable the option.
- enabled — starts a durable detached daemon (the same daemon
  ~dorg-dolt-start~ starts), matching earlier development behavior.

This option governs only that no-usable-server case of the batch/one-shot
=server= path.  Explicit ~dorg-dolt-start~/~dorg dolt start~, explicit
~dorg-dolt-stop~/~dorg dolt stop~, warm ~dorg-session~ ownership
(session-open strict-server attach via ~dorg-dolt-server--ensure-strict~),
and the interactive ~dorg-dolt-auto-server~ buffer activation above
(session-scoped ~dorg-dolt-server--ensure-strict~) always start or attach a
server as before and are not governed by this option.

A Dolt-backed ~dorg-session~ opened with no explicit ~:transport~ is
unconditionally strict =server=; there is no session-default knob.  An
explicit ~:transport~ still wins and is validated server-only
(=auto=/=cli=/unknown fail closed).  Plain-org sessions keep the global
~dorg-sql-transport~.

For a *fresh* repository initialized with ~dorg-init~ under strict
=server= transport, DOrg starts a managed bootstrap =dolt sql-server=
immediately after bare =dolt init= and before applying schema.  The
schema apply and initial commit then use the normal strict server
transport; there is no separate bootstrap CLI transport override.

** Portable file bindings and schema migration

Dolt schema v6 and later store each source locator relative to the canonical Dolt
directory.  Moving a directory that contains both the store and its source
therefore needs no rebind.  An ordinary bind may create only the initial root
of an empty store; a miss in a nonempty store refuses instead of guessing or
minting a blank root.  Use explicit ~dorg import --mode bootstrap~ to add a
document, or ~dorg dolt rebind DIR FILE --root-id N --base HASH~ to repair one
known moved binding without touching file bytes.

The current public schema is version 8.  Version 6 and 7 stores have
supported explicit migrations, walked forward one version at a time by one
operator run: v6 to v7 adds the receipt table, and v7 to v8 converts absolute
heading levels to parent-relative offsets, refusing an inconsistent hierarchy
before any write and validating the result before commit (see
[[file:schema.org][docs/schema.org]]).  History reads of commits made before
v8 decode their own schema.  Pre-v6 development stores have no supported
migration path and are refused before any write, so recreate only those stores
from their Org source.  Ordinary access never upgrades an existing store,
regardless of ~dorg-schema-auto-migrate~.  Operators run
~M-x dorg-migrate-schema~ only after every required extension is registered in
the running DOrg, a
DOrg-managed sql-server is available for the store, and non-cooperating SQL
clients are quiesced.  Offline / one-shot-CLI schema upgrade is not a supported
operator path in this release; a CLI-pinned migration request refuses before
lease acquisition, server startup/attachment, resolver evaluation, or writes.
Use ~dorg dolt start PATH~ (or ~M-x dorg-dolt-start~) to establish the managed
server route first.  Disaster-recovery CLI seams remain internal diagnostics,
not a standing schema-upgrade mechanism; the release-incident ~dolt revert~
exercise was a rehearsed recovery action, not an upgrade substitute or standing
authority for future schema repair.

~dorg-sql-cli-arg-max-threshold~ (=131072=) bounds CLI argument size:
short queries pass to =dolt= as a =-q= argument, but a large batch (for
example, a bulk import) can exceed the operating system's =ARG_MAX=
limit and fail with "Argument list too long".  Queries whose UTF-8 byte
length reaches this threshold are streamed to =dolt= over stdin instead,
where no argument-length limit applies.

* Managed clocks (opt-in Emacs)

The optional =dorg-clock-emacs= package routes =org-clock-in=,
=org-clock-out= and =org-clock-cancel= through a named Dolt clock scope
before Org edits a CLOCK line.  Load it explicitly and enable it in each
Org task buffer that should participate:

#+begin_src emacs-lisp
(require 'dorg-clock-emacs)
(dorg-clock-emacs-enable
 '(:dolt-dir "/path/to/clock-store" :root-id 100)
 "71" "America/Los_Angeles")
#+end_src

The scope and every target heading need stable =DORG_ID= values.  A Dolt task
store needs a =store-id= in =dorg_meta=, created on new-store initialization or
by =dorg dolt identify DIR= for an older store.  A plain task file needs a
=#+DORG_STORE_ID:= root keyword.  Clock reads never create either identity.  A plain
file can supply a task reference while Dolt owns the clock; enabling the
adapter never turns a plain file into a clock authority.  Reconciliation
reads the authority on enable and periodically while Emacs is idle.  It
does not start or stop a clock.  A dirty buffer defers direct clock actions;
a TODO completion can stop its managed clock after the keyword edit, while
file freshness and lock checks still apply.  A foreign lock defers actions;
an unknown apply response retains the exact intent for
=M-x dorg-clock-emacs-retry-pending=, preserving its operation ID and base.
Use =M-x dorg-clock-emacs-reconcile= to refresh the local indicator.
Native Org clock hooks, idle resolution, history selection and automatic
TODO switching caused by clock actions do not run for managed actions.  Stock Org clocking in
buffers without this mode remains independent of the managed authority.

See [[file:api.org::*Managed clock lifecycle][the clock API]] for immutable
requests, authority and task-reference contracts.  Enabling the adapter
requires an existing scope heading in that authority; the numeric identities
in the example are placeholders, not an automatically provisioned scope.

* Customizing

Every option/hook in the table above is a defcustom in the single
~dorg~ customize group.  Run =M-x customize-group RET dorg= to browse
and set them with live docstrings and type checking, or =C-h v VAR RET=
to inspect one variable.  ~dorg-sql-transport~ is deliberately outside
Customize; inspect it with =C-h v= or let-bind it in code that needs an
explicit policy.
