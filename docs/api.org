This document is the canonical reference for the dorg public command
API: the query and mutation languages used by Elisp, the =bin/dorg= CLI
and ~dorg serve~.  Source arguments and result serialization differ by entry
point; those contracts are specified below.

Inline markup convention in the DOrg docs: ~code~ denotes syntax (Elisp
forms, symbols, keywords, function names, JSON fields, commands/options, and
SQL fragments); =verbatim= denotes literal non-code text such as file paths,
exact strings, environment settings, and externally displayed values.

The per-module Elisp symbol tables and the internal module dependency
diagram are a contributor reference, not part of the public API unless
explicitly identified as public below.  They are retained in the
[[*Module dependency map][module reference]] (the dependency map and per-module
symbol tables).

* Surface parity

The same command language is reachable from three surfaces.  Their
current coverage, by capability:

| Capability                        | Elisp API | CLI (=bin/dorg=) | Interactive (Emacs)          |
|-----------------------------------+-----------+------------------+------------------------------|
| Query (full ~dorg-ql~)            | yes       | yes              | yes                          |
| Convenience reads (id/prop/tag/…) | yes       | yes              | yes                          |
| Mutation (typed DSL)              | full      | full             | ~dorg-set-property~ only     |
| Import / bootstrap                | yes       | yes              | ~dorg-setup~ (first ingest)  |
| History                           | yes       | no               | yes (view/refresh/restore)   |
| Doctor                            | yes       | yes              | yes                          |
| Server lifecycle                  | yes       | yes (+ =rebind=) | yes (+ =compact-check=)      |
| Refresh / materialize             | yes       | n/a              | yes                          |
| Managed clocks                    | yes       | no               | opt-in Org clock adapter     |

Interactive mutation helpers cover less than the general mutation API;
managed clock actions additionally use the opt-in Org adapter.  History has
no CLI verb.  Downstream programs use the Elisp API or CLI for the general
query/mutation languages; clocks use the Elisp owner API.

The executable plain-Org/Dolt capability contract is maintained only in
=tests/dorg-api-tests.el= as =dorg-test-api--capability-matrix=.  It records
the source kind, identity policy, supported/refused/pending status, independent
postimage or typed refusal pair, and its controls; this document intentionally
does not duplicate that test-side table.

* Public Command API

DOrg exposes one core query/mutation command surface with two verbs — =query=
(read) and =mutate= (write) — usable from three transports:

- *Elisp*: ~dorg-api-execute~ (and the ~dorg-command-*~ facade);
- *CLI*: =bin/dorg query= / =bin/dorg mutate=;
- *HTTP*: ~dorg serve~'s =/query= / =/mutate= routes.

The CLI =mutate= and HTTP =POST /mutate= share the same source-construction
and command handler path in ~dorg-app.el~; the HTTP route exposes the CLI verb
unchanged (it is serve-clean).  Neither transport exposes the
~:identity~ policy — both resolve to the backend-derived ~dorg~ default (see
[[file:mutate.org][docs/mutate.org]], /Identity policy/).  A non-~dorg~ policy (~(:property K)~ or
=none=) is set programmatically only, on the Elisp descriptor or the binding's
registration; there is no HTTP-specific default.

The two verbs share *one selector sublanguage*.  The read-side
~dorg-ql~ =where= predicate language ([[file:query.org][docs/query.org]]) is *also* the
mutation target language: ~(on (where QUERY) ACTION...)~ selects exactly
the headings ~(query (where QUERY))~ would return, then mutates them.
Query and mutate are deliberately *not* merged into a single unrestricted
transformation language; selection and mutation remain
auditable, separately specified steps joined only by the shared selector.

*Selection is heading-granular.*  Both verbs select *headings*: every
predicate ([[file:query.org][docs/query.org]], ~(keyword …)~ included) matches a real
heading, and ~(where QUERY)~ expands those hits through one target algebra.
The resulting target set may mix integer ids and extern keys under a
~(:property K)~ binding: K-bearing hits use K; keyless hits with an existing
=DORG_ID= use that id.  Sub-heading entities (properties, keyword occurrences,
planning, items) are addressed only relative to a host, never selected
independently.  Reads can end in =select= to project named scalar columns
from the selected headings; mutation target queries reject =select=.  The
level-0 =document= host is outside the query domain;
document-owned file-level keywords are edited only by naming =document= directly
(~(on document …)~), never via ~(where …)~.

** Read entry hierarchy

~dorg-ql-select~ is the canonical public read engine entry point.  It
validates one atomic or composable query form, resolves the source/backend
adapter, runs the read against plain-org, Dolt, or model-list storage, and
returns the canonical result plists:

#+begin_src emacs-lisp
(:heading-id ID :marker MARKER-OR-NIL :title TITLE :properties ALIST)
#+end_src

With terminal =select=, each row instead carries =:heading-id=, =:marker=
and an ordered =:values= alist with opaque string column names.  This keeps
heading identity separate from projected values.  See
[[file:query.org][query projection]] for forms and types.

Other read-facing functions are purpose wrappers over that engine, not
competing read engines:

| Entry point                                   | Purpose |
|-----------------------------------------------+---------|
| ~dorg-ql-select~                              | Canonical read engine: query validation, source/backend dispatch, and result plist shape. |
| ~dorg-ql-select-snapshot~                     | One-invocation internal envelope: rows, generic source identity, Dolt root when applicable, typed data snapshot, and extension-context digest. |
| ~dorg-ql-snapshot-public~                     | Pure public projection of one snapshot: strips markers while retaining opaque string columns and common source/root/snapshot/context/results/count data. |
| ~dorg-command-run-query~                      | UI-free machine boundary: calls ~dorg-ql-select~, returns the same results, and preserves typed ~dorg-ql-error~ conditions/data.  Interactive commands use a message-only =user-error= adapter; CLI/serve map the typed condition to their envelope. |
| ~dorg-session-query~                          | Warm-lifetime wrapper: refreshes a session when stale, reuses a token-keyed result cache, calls the same query engine, and projects host-safe results by default. |
| ~dorg-find-heading-by-id~                     | Convenience sugar for ~(id ID)~; returns the ~dorg-ql-select~ result shape. |
| ~dorg-find-headings-by-property~              | Convenience sugar for ~(property KEY VALUE)~; returns the ~dorg-ql-select~ result shape. |

Downstream integrations that need the general read API should call
~dorg-ql-select~ directly, or ~dorg-command-run-query~ when they are
implementing a UI-free command boundary that must retain machine-readable
query errors.  Use ~dorg-session-query~ only when holding a managed warm
session, and use ~dorg-find-*~ only for the two legacy one-predicate lookup
cases.

** Raw SQL extension escape hatch

The command API above remains the ordinary public API.  Extension authors who
intentionally accept coupling to the Dolt relational schema may use the raw SQL
family as a development extension escape hatch.  Its behavior is tied to the
versioned schema in [[file:schema.org][docs/schema.org]].  Its compatibility is
schema-versioned and is not part of the command-API stability promise.

This surface is Elisp/Dolt-facing.  It is not a third CLI or HTTP verb, and it
does not provide selector semantics, mutate safety rails, or command-envelope
result shapes.  Use =query= / =mutate= for ordinary clients; use raw SQL only
when an extension needs schema-level access and is prepared to track schema
versions.

| Symbol | Role |
|--------+------|
| ~dorg-sql~ | Execute a SQL statement and return result rows as alists. |
| ~dorg-sql-batch~ | Execute multiple statements; with a commit message, wrap the batch in a transaction and commit it. |
| ~dorg-sql-quote~ | Quote a Lisp value as a SQL string literal. |
| ~dorg-sql-escape-string~ | Escape string content for SQL literals. |
| ~dorg-head-commit~ | Read the current Dolt HEAD commit token. |
| ~dorg-commit~ | Stage all changes and create a Dolt commit. |

Raw SQL callers are responsible for preserving DOrg schema invariants: root
scoping, foreign keys, sibling and item ordering, item kind/detail-table
consistency, property and drawer ordinals, and commit
discipline.  Quote values through ~dorg-sql-quote~ or
~dorg-sql-escape-string~; do not hand-concatenate untrusted values into SQL.
For multi-statement writes that should be atomic and durable, use
~dorg-sql-batch~ with a commit message rather than a sequence of independent
~dorg-sql~ calls.  Prefer ~dorg-head-commit~ and ~dorg-commit~ over shelling out
to Dolt directly.

** The mutate verb at a glance

#+begin_src emacs-lisp
;; Elisp — dry-run, then apply
(dorg-api-execute '(on (id 100) (set (property "STATUS") "DONE")) :mode 'dry-run)
(dorg-api-execute '(on (id 100) (set (property "STATUS") "DONE")) :mode 'apply)

;; COMMENTED is an intrinsic boolean heading slot: t adds COMMENT, nil clears it.
(dorg-api-execute '(on (id 100) (set (heading commented) t)) :mode 'apply)
(dorg-api-execute '(on (id 100) (set (heading commented) nil)) :mode 'apply)

;; Birth-hidden construction: COMMENT is present in the first committed image.
(dorg-api-execute
 '(insert (heading (title "Resolution") (commented t))
          (under (key "task-1")))
 :mode 'apply)

;; Insert one raw line at the front of the first exact-name generic drawer.
(dorg-api-execute
 '(on (id 100)
      (insert (drawer-line "LOGBOOK") (before-first) "- note"))
 :mode 'apply)
#+end_src

#+begin_src sh
# CLI — exactly one of --dry-run / --apply is required
dorg mutate '(on (id 100) (set (property "STATUS") "DONE"))' --dry-run
dorg mutate '(on (id 100) (set (property "STATUS") "DONE"))' --apply
#+end_src

#+begin_example http
# HTTP
POST /mutate?mode=dry-run
(on (where (property "STATUS" "OPEN")) (set (property "STATUS") "DONE"))
#+end_example

The complete mutate grammar — public DSL, typed patch IR v2, occurrence
vs sequence keyword semantics, the typed execution boundary, the
command envelope, dry-run/apply safety gates, and the response/error
shapes — is specified in [[file:mutate.org][docs/mutate.org]].  The rest of this part states
the cross-cutting command contract that both verbs honour.

The =commented= heading field accepts only exact =t= or =nil=.  It projects
to the intrinsic heading =COMMENT= marker, not to a property or section.
Non-boolean values fail with typed =invalid-target= before mutation.  The same
singleton value domain is available as an =insert heading= constructor clause;
explicit =nil= is preserved as a present value.  A supported plain-org
constructor writes the requested COMMENT state in the first image, rather than
creating a visible heading and hiding it in a second step.

The drawer-line grammar is target-agnostic.  A downstream external-key caller
may compose the same action as:

#+begin_src emacs-lisp
(on (key ID)
    (insert (drawer-line "LOGBOOK")
            (before-first) RAW-LINE))
#+end_src

The direct key is the canonical exactly-one identity target; it is not part of
the action syntax.

** Source descriptors

The source names storage, not a domain object.  Entry points currently
accept different source representations.  For ~dorg-api-execute~ and
mutation intent construction, the accepted forms are
([[file:mutate.org][docs/mutate.org]], /Source descriptors/):

| =SOURCE=                       | Resolves to                             |
|--------------------------------+-----------------------------------------|
| =nil=                          | the current buffer's backend |
| a buffer (object or name)      | that buffer's registered backend        |
| ~(:buffer BUFFER)~             | a registered live buffer                |
| ~(:file PATH)~                 | an explicit plain-org file              |
| ~(:dolt-dir DIR :root-id ID)~  | an explicit Dolt root                   |

~dorg-ql-select~ accepts nil (current buffer), a buffer, a nonempty list of
heading models, or an ephemeral Dolt ~dorg-registration~.  It does not accept
mutation descriptor plists.  An empty list is nil and therefore means the
current buffer, not an empty model source.  ~dorg-session-open~ accepts a
buffer or file path.  Keep these entry-specific contracts explicit in
consumer adapters.

On the CLI source selection uses =-f/--file= and =--dolt-dir= / =--root-id= flags;
over HTTP they are request parameters.  For CLI =mutate=,
=--dolt-dir DIR --root-id ID= selects the explicit Dolt root directly;
=--dolt-dir= without =--root-id= keeps the existing file-backed forced
binding path, and =--root-id= without =--dolt-dir= is a usage error.  A
plain file needs no registration: plain-org is its default backend.
Queries use a file/buffer binding; =--root-id= is not a query source shortcut.

*** Identity-stability contract

Snowflake ids are engine-immutable: typed mutation allocates them in the
engine, while administrative import completes them once in its isolated parse
model.  They are never rebound, duplicate ids fail loud, and direct =DORG_ID=
writes are rejected.  That does not make every id-bearing handle
equally durable across storage media:

| Medium / target form        | Stability contract                                      |
|-----------------------------+---------------------------------------------------------|
| Dolt root / ~(id N)~        | Durable database primary key.                           |
| Id-bearing plain-org (~dorg~) | Durable only while the ~:DORG_ID:~ drawer text remains. |
| ~(:property K)~ plain-org   | K-bearing headings project by extern key.  A descriptive where hit lacking K may use an existing =DORG_ID=; a K-less and DORG_ID-less hit is not writable. |
| ~(under ...)~ / sibling anchor | Same class as the referenced target; accepts direct ~(key V)~ for bounded external-key structural operands. |
| ~(where ...)~               | No durability by design; confirm with ~:expected-targets~. |
| ~(key V)~                   | External-key identity; recommended for ~(:property K)~ sources and stored references.  The key NAME comes from the identity policy, not the form. |

The numeric fallback above is restricted to descriptive ~(where ...)~
projection.  Direct ~(key V)~ and structural key operands remain exact K-only
selectors and never fall back.  DOrg consumes an existing =DORG_ID=; it does
not provision one on a faithful plain-org heading.

If a plain-org drawer is lost, the heading silently receives a fresh id on
the next identity-allocating path; there is no tombstone.  To an id-holding
caller, delete+recreate is indistinguishable from an id change.  A base token
catches source divergence, not identity rebirth.

** First-class mutation intent

Elisp callers that need to inspect, preview, approve, and apply one logical
request can use a mode-neutral, immutable intent value:

#+begin_src emacs-lisp
(let* ((intent
        (dorg-api-make-mutation-intent
         '(on (where (property "STATUS" "OPEN"))
              (set (property "STATUS") "DONE"))
         :source '(:file "/tmp/tasks.org")
         :op-id "status-close-17"))
       (preview (dorg-api-execute intent :mode 'dry-run))
       (approved
        (dorg-api-mutation-intent-with
         intent
         :base (plist-get preview :base)
         :expected-targets (plist-get preview :targets))))
  (dorg-api-execute approved :mode 'apply))
#+end_src

The public operations are ~dorg-api-make-mutation-intent~,
~dorg-api-mutation-intent-p~, the copy-returning
~dorg-api-mutation-intent-form~ and ~dorg-api-mutation-intent-options~, and
the functional ~dorg-api-mutation-intent-with~.  Construction accepts exactly
~:source~, ~:base~, ~:expected-targets~, ~:allow-broad~, ~:save~,
~:message~, ~:op-id~, and ~:lock-timeout~.  Mode is supplied only to ~dorg-api-execute~;
supplying construction options beside an existing intent is =malformed=.
Derive a new value instead.

Construction owns mutable list, string, and vector data, and inspection
returns detached copies.  A live buffer source remains an external identity
handle rather than a cloned buffer; execution resolves it afresh and the
normal base/CAS gates protect its changing contents.  Forms and query/key
targets are also normalized and resolved afresh for every dry-run or apply,
so an intent is not a frozen private patch plan.

The value contains no mode, extension payload, caller read set, candidate
state, SQL, or private typed patch IR.  DOrg derives its native bounded read
scope from the normalized patches at the exact execution revision.  The
response still carries ~:intent~ as detached public forms, never as the opaque
value.  The value is process-local and has no serialization or durable replay
contract; persisted plans remain a separate future problem.

The intended one-way boundary is: immutable request -> normalized typed
patches -> canonical candidate post-state -> derived extension effects.  The
candidate post-state and its automatic index projectors have landed: derived
extension effects are a pure function of that DOrg-owned context, and the
per-execution ~:extension-inputs~ caller-payload channel is retired (fails
closed; see [[Index projectors (~:extension-inputs~ retired)]]).

** Elisp execution options

~dorg-api-execute~ accepts three apply-oriented Elisp options in addition to the
mode and safety options.  Each option takes effect only when the caller
supplies it; omission uses the default described below.

| Option            | Effect |
|-------------------+--------|
| ~:save BOOL~      | For an apply against a live plain-org buffer, =t= persists the changed buffer through DOrg's atomic save path; nil or omission leaves it modified and unsaved.  An explicit ~(:file PATH)~ source is atomically rewritten by apply itself.  Dolt does not use this option. |
| ~:message STRING~ | Supplies the Dolt commit message for apply.  Omission (or nil) uses the engine default.  It has no plain-org persistence effect. |
| ~:lock-timeout SECONDS~ | Bounds a saved local plain-Org writer-gate wait.  Must be finite and nonnegative.  Omission uses the fixed DOrg default. |

None of these options can turn a dry-run into a write: ~:mode 'dry-run~ always takes
the plan path and neither saves a file nor creates a Dolt commit.  The
file-backed CLI apply supplies ~:save t~ internally; ~:save~ and ~:message~
are not separate public CLI flags.  The CLI exposes =--lock-timeout= and a
read-only =dorg lock inspect PATH= operator command.  The saved-file gate and
its limits are specified in [[file:mutate.org][Mutation]].

** Mode contract (dry-run vs apply)

The mutate verb requires *exactly one* of =--dry-run= or =--apply=
(~:mode 'dry-run~ / ~:mode 'apply~ in Elisp).  There is *no default
apply*: omitting both, or supplying both, is a =mode-error= (a
=user-error= / HTTP 4xx), never a silent write.  =query= is always
read-only and takes no mode.

- *dry-run* — normalize and plan only.  Returns the normalized command
  data, typed patch IR, resolved target ids, affected
  ids where known, the current source token, and any validation errors.
  It *never* mutates.
- *apply* — runs the same normalization path, then executes under the
  safety gates (base token, expected-target-set, broad-write threshold).

Planning *is* =mutate --dry-run=.  There is no separate public =plan=
command and no persisted/executable plan artifact in the mutation command API.

** Response envelope

Structured command-boundary responses (CLI =--json= and HTTP) use one
top-level envelope:

#+begin_src json
{"ok": true,  "data": {...}, "error": null}
{"ok": false, "data": null,  "error": {"reason": "...", "message": "...", "details": {...}}}
#+end_src

Public JSON keys are kebab-case everywhere, matching Lisp keyword spelling
without the leading colon: ~:heading-id~ -> ="heading-id"=,
~:base-commit~ -> ="base-commit"=, ~:dolt-dir~ -> ="dolt-dir"=.  Snake
case and camelCase are not public wire keys.

The =query= data payload carries =:command query=, =:source=, =:root=,
=:snapshot=, =:context-digest=, =:results= and =:count= from one invocation.
Default rows contain =:heading-id=, =:title= and =:properties=; projected rows
contain =:heading-id= and =:values=.  Live markers are not serialized.
Ranked BM25 uses the distinct search snapshot described in
[[file:query.org][query.org]].

The =mutate= data payload is:

#+begin_src emacs-lisp
(:ok t :command mutate :mode dry-run|apply
 :intent (FORM...)                      ; the public forms as written
 :patches (TYPED-IR...)                 ; canonical typed patch IR v2
 :targets (IDS...)                      ; resolved concrete target ids
 :affected (:created (..) :changed (..) :deleted (..))   ; apply
 :supported BOOL :unsupported (CLASSIFICATION...)
 :base TOKEN?
 :base-commit C? :base-revision TOK? :new-token TOK?
 :invalidation (:roots (ROOT-ID...)
                :ext-dirty ((EXTENSION . SCOPE)...)
                :head C? :dolt-dir D? :file F?)?)
#+end_src

This is the public reshape over the IR-native engine boundary:
~dorg-api-execute~ calls the typed mutation engine with patch IR directly,
adding ~:intent~ and ~:patches~.  Consumers bind to ~:intent~, ~:patches~, ~:targets~,
~:affected~, ~:supported~, and ~:unsupported~.  The CLI renders
a human summary in text mode; structured modes place this payload under
=data=.  These mutate fields are not duplicated at the top level.

For a plain-org constructor, ~:affected :created~ reports the freshly minted
numeric identity only under ~dorg~ identity.  A source bound by
~(:property KEY)~ keeps that file-owned identity, writes no synthetic
=DORG_ID=, and therefore reports no numeric created id.

~:invalidation~ is *present only when the engine result contains that key*;
the API preserves its value exactly (including an explicit nil for an empty
net-effect result) and never synthesizes it for plain-org or another result
that omits it.  ~:roots~ and ~:ext-dirty~ are the stable cache-scope fields.
A Dolt apply additionally carries its advancing ~:head~ and source identity
(~:dolt-dir~ / ~:file~).  A dry-run in which an index projector ran may carry a
preview containing only the stable fields, deliberately without an advancing head.
Consumers comparing dry-run with apply compare the stable scope fields, not
the apply-only freshness token.

** Compact receipts and retired derived-model responses

An op-id Dolt apply stores a compact operation receipt atomically with its data:
=op_id=, immutable =gen_id=, =intent_digest= and =ts=.  Same-op-id/same-intent
retry returns the original ~:new-token~, echoed ~:op-id~ and ~:idempotent t~
without replaying data SQL.  Different intent remains terminal
=idempotency-key-mismatch=.  Generation-safe recovery requires exactly one
added transition for the quoted generation id; missing or ambiguous history
fails closed.  Pruned current evidence cannot promise retained idempotency.

~:return-candidate-models~ is retired.  Its presence, including an explicit nil,
is =malformed= with ~:option :return-candidate-models~ through the existing
closed option domain at construction, functional replacement and raw execute.
Raw execute still checks mode first.  Unrelated unknown raw keywords retain
their historical ignored behavior, domain order and first-value handling.
There is no accepted-and-ignored request or new retired-option registry.

~:candidate-models~ and ~:postimages~ are no longer mutation response fields.
Replay neither reads a derived payload nor reconstructs a model.  The receipt
table and its nullable legacy column stay unchanged; historical column bytes are ignored,
not rewritten.  Full pre-commit core/item/owner/extension parity still gates every
commit.  A caller needing state must use an existing exact-revision read with an
explicit root/id scope and the returned commit, not infer moved/deleted or
unchanged requested scope from current HEAD.

** Index projectors (~:extension-inputs~ retired)

The per-execution ~:extension-inputs~ caller-payload channel is *retired*.
Registered *index projectors* now run automatically as a pure
function of the DOrg-owned candidate-state context (~dorg-ext-index-context~)
DOrg builds after core simulation — they accept *no* caller
payload, consume no implicit state, and are neither selected nor fed by the
client.  Supplying ~:extension-inputs~ to ~dorg-api-execute~ *fails closed* with
a typed ~dorg-api-error~ (reason =unsupported=, ~:detail extension-inputs-retired~)
before any storage is touched; first-class mutation intents still reject the key
as foreign authority.

*What runs.*  For each registered extension whose ~:capabilities~ include the
mutation's source kind and which declares a ~:project~ index projector, DOrg runs
the optional ~:validate~ then ~:project~ against the index-context.  ~:project~
returns a list of *typed row deltas* — ~(:table NAME :insert ((COLUMN . VALUE) …))~
or ~(:table NAME :delete WHERE)~ — NOT SQL text.  DOrg (not the extension)
generates the SQL from the literal, candidate-derived values, so an effect cannot
read database state, join, subquery, or reach another table.  Each effect is
confined to the extension's declared ~:read-tables~ (a single unqualified, owned,
non-core table with identifier-safe columns); a core/foreign/unowned/qualified
table, an unsafe identifier, or a malformed effect *fails closed* before
persistence.  The generated SQL commits in the SAME Dolt transaction as the core
mutation (atomic; a stale-CAS replan discards the prior effects and re-derives
from the replacement candidate).

*Root aggregates (accumulators).*  A projector whose derived state includes a
root-wide aggregate, such as a document frequency or a corpus total, need not
derive the whole root.  It declares the aggregate table in ~:read-tables~ with
~:accumulate (KEY-COLUMN …)~, its complete key including its scope column.  It
then returns *accumulator effects* for that table instead of rows:
~(:table NAME :accumulate KEY-ALIST :add ((COLUMN . INTEGER) …) :xor ((COLUMN
. HEX64) …) :initial ((COLUMN . VALUE) …) :prune-zero COLUMN)~.  Integers under
addition and 256-bit lowercase-hex digests under xor are commutative,
associative and invertible, so folding any sequence of deltas from the
identity is order-free and incremental state equals a fresh rebuild.

Accumulators never reach SQL.  At plan time DOrg reads exactly the touched
keys' rows AS OF the plan base (one keyed revision read per table, never the
live head or working set).  It folds the deltas into ordinary literal row
effects (~:delete~ + ~:insert~ for a stored key, a lone ~:insert~ for a new
one), revalidates them, and hands them to the same SQL generator, commit
proof and drift audit as every other effect.  A new key is born from the
identity plus ~:initial~; a ~:prune-zero~ column reaching zero
deletes its row; an unchanged row emits nothing; a negative count fails
closed.  The commit lands only while the in-gate HEAD still equals the plan
base, so a moved base replans with fresh priors.  A table takes either
accumulator or row effects, never both.  Every effect of an accumulator
extension, row effects included, must address a root its context establishes
(the root, or a cross-root move's source and destination); any other root
fails closed with ~root-outside-context~ before a prior is read.

Exactly one accumulator table is the extension's completeness ~:marker~, with
its required non-scope keys per root (~t~ when the key is the scope column
alone), declared at registration.  Each touched root is then judged in one of
three states:
- *built*: every required marker row is present, and the root folds;
- *unbuilt*: none is present.  If the root had headings at the base, the
  extension's effects for it are dropped and its index stays wholly absent,
  never partial; if it was empty, its first write births every required
  marker row;
- *inconsistent*: some required rows are present but not all.  The mutation
  fails closed with ~derived-index-inconsistent~ naming
  ~dorg-ext-rebuild-index~.  This is the only state in which a derived index
  blocks a write.

| Caller | Priors read at | Guard |
|--------+----------------+-------|
| mutation, cross-root mutation, dry-run | plan base (=:plan-base=) | in-gate HEAD = plan base, else replan |
| import | captured head | HEAD = base and a clean working set |
| rebuild audit and repair | none (fold from absent after the DOrg-owned clears) | repair at HEAD |
| policy upgrade | n/a | refuses every non-insert effect, accumulators included |

*Affected owner partitions.*  A Dolt index-context also exposes
~dorg-ext-index-context-owner-partitions~ for extensions that derive
identity-owner indexes.  This is a read capability on the existing
~dorg-ext-index-context~, not an extension registration callback and not a
widening of ~dorg-ext-index-context-base-image~ /
~dorg-ext-index-context-candidate-postimage~.  Those image accessors keep their
bounded core working-scope meaning from the mutation simulator.

DOrg constructs each owner partition after core simulation and before projector
collection, using the mutation source's existing identity policy as the only
owner selector.  The default ~dorg~ policy uses =DORG_ID= and makes an affected
heading its own identity owner; ~(:property K)~ uses property K and resolves the
nearest owner separately in S0 and in the candidate; ~none~ is read-only and is
refused by the mutation gate before projector execution.  There is no caller
owner id, owner closure list, no-op touch, SQL/query handle, extension callback,
or source-specific downstream vocabulary.

Each partition represents one affected identity owner in one root.  Deletes
carry base tombstones; creates carry candidate ownership; same-root and
cross-root moves expose the source and destination owner partitions needed to
derive removal and insertion effects.  A nested identity-owned child is excluded
from its parent's owner-local image and appears as its own owner only when it is
affected.  Ownerless root/config keyword edits are not widened into partitions;
root data remains the existing core-scope row, so configuration rows such as
=embead_config_values= remain derivable from root items without a separate owner
scope.

| Accessor | Contract |
|----------+----------|
| ~dorg-ext-index-context-owner-partitions~ | Fresh list spine of affected owner partitions. |
| ~dorg-ext-owner-partition-root-id~ | Root that owns this partition. |
| ~dorg-ext-owner-partition-owner-id~ | Heading id of the identity owner. |
| ~dorg-ext-owner-partition-owner-key~ | Fresh copy of the identity property key (=DORG_ID= or K). |
| ~dorg-ext-owner-partition-owner-value~ | Fresh copy of the owner's identity value. |
| ~dorg-ext-owner-partition-parent-owner-id~ | Nearest ancestor identity owner's heading id, or nil. |
| ~dorg-ext-owner-partition-parent-owner-value~ | Fresh copy of the nearest ancestor owner value, or nil. |
| ~dorg-ext-owner-partition-affected-ids~ | Fresh list of affected heading ids that contributed to this owner. |
| ~dorg-ext-owner-partition-affected-paths~ | Fresh list of plists =(:id ID :side before/after :path IDS)= proving each affected heading's path to the owner in the relevant image. |
| ~dorg-ext-owner-partition-base-image~ | Fresh id -> ~dorg-heading~ hash for the owner-local S0 image. |
| ~dorg-ext-owner-partition-candidate-postimage~ | Fresh id -> ~dorg-heading~ hash for the owner-local candidate image. |

The owner-local images include the owner heading and the complete dense ordered
owner-local descendant partition DOrg can prove from the affected owners,
excluding nested identity-owned partitions.  The parent-owner fields name the
nearest ancestor identity owner, not necessarily the literal structural parent,
so an owner nested below plain wrapper headings can still derive a stable parent
identity.

All partition objects are DOrg-owned, vaulted, immutable, and copy-on-read.
Projectors consume the returned ~dorg-heading~ models directly and return only
manifest-confined typed row deltas.  They must not query around the context,
render/reparse Org text, persist partition state, construct their own owner
closures, or supplement partitions with caller-supplied authority.  Partition
construction is batched and bounded by affected owners, ancestor paths, and
owner-local content, using explicit id hydration rather than a whole-root load
fallback.  Broken ancestry, cycles, ambiguous owner resolution, load failure,
and stale/mismatched materialization fail closed before persistence.

The context ~candidate-id~ covers every projector-visible owner-partition field
in addition to the existing candidate postimage.  On an accepted stale-CAS
replan, DOrg discards the stale context and rebuilds owner partitions from the
replacement base/candidate before rerunning projectors.  This capability is
limited to identity-owner-indexed projections; it is not a universal graph,
history, or global extension scope mechanism.

*Dirty scope.*  The separate ~:dirty-scope~ callback is retired: dirty/invalidation
scope is derived deterministically by DOrg from the single projector result (the
owned tables the effects touched) and published in ~:invalidation :ext-dirty~ at
the committed revision.

*Response.*  The mutate response surfaces ~:extensions~ — an alist of
~(NAME . (:statements N))~ summaries — whenever an index projector actually ran,
plus ~:invalidation~ (stable ~:roots~ + ~:ext-dirty~; apply carries an advancing
commit/head token, a dry-run a preview without one).  Derived SQL
(~:ext-sql~ / ~:db-ops~) stays engine-internal.  A dry-run runs the same
derivation and reports the same stable summary + invalidation fields as apply, but
persists nothing.

*Operation-qualified consistency.*  Before apply, DOrg checks that immutable S0,
the candidate postimage, and the declared typed effects are mutually consistent: a
candidate that drops a child identity the typed request preserved is refused
(typed =invariant=, ~:detail undeclared-child-drop~).  This is operation-qualified,
not a cardinality veto — an explicit typed deletion (single or subtree) of any
number of children is accepted.

** Error model

Command-envelope validation failures use ~dorg-api-error~, whose data is
~(MESSAGE PLIST)~ — the same shape as ~dorg-mutate-error~.  Engine failures
retain their typed engine leaf.  Two API-leaf accessors read command validation
errors without parsing the message:

#+begin_src emacs-lisp
(dorg-api-error-reason ERR)  ; the :reason symbol
(dorg-api-error-data   ERR)  ; the whole structured plist
#+end_src

*Rooted taxonomy.*  ~dorg-api-error~ is one leaf of a single public error
taxonomy rooted at ~dorg-error~ (=dorg-error.el=).  Command, engine, query,
and administrative binding leaves — ~dorg-api-error~, ~dorg-mutate-error~,
~dorg-ql-error~, and ~dorg-binding-error~ — are children of ~dorg-error~, so a
single handler catches *any* dorg failure:

#+begin_src emacs-lisp
(condition-case err
    (dorg-api-execute FORM)
  (dorg-error                       ; catches api / mutate / ql alike
   (message "%s" (dorg-error-reason err))))
#+end_src

Two generic accessors span the whole taxonomy — ~dorg-error-data~ returns
the structured plist (or nil for a non-dorg condition) and
~dorg-error-reason~ its ~:reason~.  Query errors carry the same
~(MESSAGE PLIST)~ shape as the other public leaves.  The typed leaves are preserved: catching a specific
~dorg-api-error~ / ~dorg-mutate-error~ / ~dorg-ql-error~ and using the
per-symbol accessors still works exactly as before (reparenting is
additive).

The closed reason set reuses the engine reasons — =invalid-op=,
=invalid-target=, =unsupported=, =stale=, =invariant= (see
[[file:mutate.org][docs/mutate.org]]) — plus four command-envelope reasons: =mode-error=
(neither/both of dry-run/apply), =expected-targets-required= (a
query-scoped apply with no ~:expected-targets~), =target-set-changed= (a
query-scoped apply whose re-expanded target set differs from
~:expected-targets~), and =broad-write-refused= (an apply over more than
~dorg-api-broad-write-threshold~ targets without =--allow-broad=).  A supplied
~:extension-inputs~ (the retired caller-payload channel, see [[Index projectors
(~:extension-inputs~ retired)]]) fails closed with reason =unsupported= and
~:detail extension-inputs-retired~.  Over HTTP, client-side request failures
map to 4xx and serialize through =error.reason=,
=error.message=, and optional =error.details=.

Engine failures reached through ~dorg-api-execute~ retain their more precise
~dorg-mutate-error~ leaf rather than being relabeled, but both leaves share the
~dorg-error~ root and the same structured data shape.  In particular, Dolt
commit-time concurrency and constraint failures expose only the stable details
=serialization=, =concurrent-state-unproven=,
=sibling-order-planner-defect=, =constraint=, =database-failure=, or
=rollback-failed=.  A transport-typed loss while =DOLT_COMMIT= is in flight is
the existing =indeterminate= reason with stable detail =commit-indeterminate=;
it is terminal and must be reconciled with the same op-id.  Details may include
attempt/base/scope facts, ~:transaction-phase in-commit~, numeric ~:db-code~,
and the normalized =uq-heading-sibling-order= constraint.  Raw MySQL messages,
SQL text, SQLSTATE prose, duplicate values, and ~:underlying~ are not part of
the API contract.  See [[file:mutate.org][docs/mutate.org]], /Dolt attempt and
rollback law/.

** Migration from =set=

DOrg does not expose the pre-release =dorg set= CLI command or the
=POST /set= route; use =mutate=.  The interactive Emacs helper
~dorg-set-property~ (see the [[*=dorg-command.el=][=dorg-command.el= module
reference]]) is kept as a one-property typed mutation convenience, not as the
canonical noninteractive write API.
Migration is mechanical:

#+begin_src sh
# before
dorg set STATUS DONE --id 100
# after
dorg mutate '(on (id 100) (set (property "STATUS") "DONE"))' --apply
#+end_src

** Convenience aliases

DOrg provides the *per-predicate CLI read commands* ~dorg id~ / =dorg
property= / ~dorg tag~ / ~dorg title~ as thin convenience aliases over
~dorg query '(<predicate>)'~: each maps to the query verb with the
corresponding selector predicate, e.g. ~dorg id 100~ ≡ =dorg query '(id
100)'= and ~dorg tag work~ ≡ ~dorg query '(tag "work")'~.  They exist for
the common one-predicate reads; prefer =query= for anything composable.

The mutate *source descriptor* likewise accepts ~(:plain-org PATH)~ as an
alias for ~(:file PATH)~: both name an explicit plain-org file and are
interchangeable wherever a mutate source is taken.

One spelling was retired before the public freeze: =bin/dorg-ql= and its
=DORG_QL_FILE= environment variable (a deprecated alias for =DORG_FILE=)
were removed; invoke =bin/dorg= directly (see [[file:cli.org][docs/cli.org]]).

The selector *predicates* ~(id N)~, ~(property K V)~, ~(tag T)~, =(title
T)= are the base case of the query/=where= selector language
([[file:query.org][docs/query.org]]) and compose into ~(on (where …) …)~.

~dorg-import-document~ / ~dorg import~ is deliberately outside this ordinary
query/mutate command surface.  It is a CLI/Elisp-only administrative
whole-document bootstrap or recovery operation, requires a complete explicit
request, and is refused over HTTP.  It is not a third authoring verb.  See
[[file:import.org][docs/import.org]].

* =dorg-ql.el=
:PROPERTIES:
:CUSTOM_ID: query-library-api
:END:

| Symbol                     | Description                                       |
|----------------------------+---------------------------------------------------|
| ~dorg-ql-select~           | Run one validated query (atomic or composable) over a source |
| ~dorg-ql-select-snapshot~  | Return one source-bound =:rows= / =:source= / =:root= / typed =:snapshot= / =:context-digest= envelope |
| ~dorg-ql-snapshot-public~  | Project one snapshot to shared JSON-ready query data with opaque string row keys |
| ~dorg-ql-error~            | Typed query failure: =invalid-query= or =unsupported= |

~dorg-ql-select~ takes a ~dorg-ql~ query form and an optional source.
The query may be a historical atomic predicate (kept as an alias) or a
composable form.  ~dorg-ql-select~ validates the form up front and
dispatches both surfaces through ~dorg-ql-normalize~ to one backend-neutral
normalized AST.  The full DSL — =pipe=/=where=/=traverse=,
the boolean combinators, =field=, and structured =timestamp= windows — is
documented in [[file:query.org][docs/query.org]]; the rest of this
section describes the atomic surface and the shared dispatch/result
contract.  The identity/structural atomic forms are ~(id ID)~, =(property
KEY VALUE)=, ~(title TITLE)~, and ~(tag TAG)~.  Property and tag matches
are exact and
non-inherited; =ID= is an integer or numeric string.  The source selects
the adapter: =nil= or a buffer dispatches via the buffer's registered
backend (plain-org or Dolt); a non-empty list of ~dorg-heading~ structs
uses the model adapter. An ephemeral ~dorg-registration~ with a Dolt backend
dispatches directly to its supplied store/root, without a buffer visit or
registry lookup. For composable queries, that model-list is an ordered forest:
filter-only pipelines run over the supplied order, while traversal and
=unique= require unique non-nil heading ids and signal ~dorg-ql-error~ if
the identity contract is violated.  Results are plists with keys
~:heading-id~, ~:marker~, ~:title~, and ~:properties~ — plain-org results
carry live markers, model and Dolt results carry =nil= markers.  Terminal
=select= replaces =:title= and =:properties= with the ordered =:values=
alist described in [[*Read entry hierarchy][Read entry hierarchy]].
Unknown predicates, wrong arity, and wrong argument types signal
~dorg-ql-error~; invalid forms never fall back to a broad scan.

String comparisons may end in =~:case sensitive= or =~:case insensitive=;
omitting the option is exactly =~:case sensitive=.  The option applies only
to string values (including title/todo, property and keyword values, tag
values, and declared string extension fields).  Insensitive mode uses
per-character standard-case equivalence and, for Dolt, the documented
residual route rather than a database collation.  See [[file:query.org][the
query grammar]] for the supported forms and literal Unicode contract.

~dorg-ql-select-snapshot~ is the transport-facing counterpart for a buffer
or an ephemeral Dolt registration. It captures a Dolt revision before
extension context or data reads,
then returns =(:rows ROWS :source SOURCE :root ROOT-ID :snapshot SNAPSHOT
:context-digest DIGEST)=. =SOURCE= identifies backend kind and canonical file
when present (plus the Dolt store); =SNAPSHOT= is =(:kind dolt :head COMMIT)=
or =(:kind plain-org :content-sha256 SHA256)= for the exact text evaluated.
~dorg-ql-snapshot-public~ is the pure shared CLI data boundary. The context
digest identifies independently versioned workflow/configuration inputs; it is
not a substitute for the data snapshot.

An in-process consumer can query an existing Dolt root without opening or
materializing its Org projection:

#+begin_src emacs-lisp
(require 'dorg-ql)
(require 'dorg-repo)
(let* ((file (file-truename "/path/to/project/document.org"))
       (store (file-truename "/path/to/project/.dorg/dorg"))
       (root (or (dorg-repo-root-id store file)
                 (user-error "No DOrg root bound to %s" file)))
       (source (make-dorg-registration
                :backend (dorg-backend-dolt store root)
                :file file)))
  (dorg-ql-snapshot-public
   (dorg-ql-select-snapshot
    '(pipe (select (field title) (field todo))) source)))
#+end_src

~dorg-repo-root-id~ is a read-only lookup and refuses ambiguous or malformed
bindings; QL resolves a classification-only nil root at its captured revision
and refuses its =nil= result with ~dorg-bind-dolt~ recovery. The descriptor
names that explicitly resolved root. ~:file~ supplies source identity and the base
for relative extension configuration links, so retain the actual file even
though the query does not visit it. Load any required extension before the
query. All selected data and local extension-context reads then use the one
revision captured by ~dorg-ql-select-snapshot~; independently versioned
configuration remains identified by the context digest.

Plain Org queries use a buffer containing the source text and its actual
~buffer-file-name~. A caller may own a temporary Org buffer for that purpose
and release it after converting the result with ~dorg-ql-snapshot-public~;
the converted result contains no live markers. Keep this read buffer unchanged
during the query and never save it. Backend classification uses its binding
and source text: a projection carrying =#+DORG_DOLT_DIR:= is classified as
Dolt. The file-descriptor plists
accepted by the command and mutation APIs are not query SOURCE forms.

~dorg-ql-error~ carries ~(MESSAGE PLIST)~.  The closed top-level reason set
is exactly =invalid-query= and =unsupported=: grammar, arity, value, and
cardinality failures are =invalid-query=; =unsupported= is reserved for a
known source/backend capability refusal.  Inspect the condition through
~dorg-error-reason~ / ~dorg-error-data~ rather than parsing its message.

A timestamp/LOGBOOK predicate family is also supported, each taking a
=FROM TO= date window.  =FROM= and =TO= are each a ="YYYY-MM-DD"= string
or =nil= for an open bound, and the window =[FROM, TO]= is *inclusive* at
both ends.  A timestamp's span =[start-date .. (end-date|start-date)]= is
itself inclusive, and a predicate matches when that span overlaps the
window:

| Form | Match |
|------+-------|
| ~(scheduled FROM TO)~ | heading SCHEDULED planning timestamp in window |
| ~(deadline FROM TO)~  | heading DEADLINE planning timestamp in window |
| ~(closed FROM TO)~    | heading CLOSED planning timestamp in window |
| ~(active-ts FROM TO)~ | any active body timestamp overlaps the window |
| ~(logbook FROM TO)~   | any LOGBOOK entry timestamp overlaps the window |
| ~(property-ts FROM TO [NAME])~ | a timestamp-valued property overlaps the window (optionally restricted to property =NAME=) |

The model adapter (a list of ~dorg-heading~ structs) answers every
predicate.  On the plain-org and Dolt buffer adapters, all six predicates
-- =scheduled=, =deadline=, =closed=, =property-ts=, =logbook=, and
=active-ts= -- are lowered and resolve natively, each candidate-bounded (a
narrow SQL selector or entry-local scan, never a whole-tree load) and
reusing the one parser and window predicate so all three backends produce
identical matches.  A query on any other backend signals ~dorg-ql-error~
rather than silently widening or emptying the result.

The composable DSL (=pipe=/=where=/=traverse=, boolean combinators,
=field=, structured =timestamp= windows) lowers to the same normalized
AST and dispatches through ~dorg-ql-select~.  Composable forms run on model-list,
plain-org, and Dolt sources.  See
[[file:query.org][docs/query.org]] for the full grammar.  Fuzzy
matching, updates, and Clime commands remain out of scope for this core.

=dorg-ql.el= is a thin public facade (validation gate + backend
dispatch); the implementation lives in internal modules loaded before it:
=dorg-ql-core.el= owns the timestamp predicate metadata (the single source
of truth from which the predicate set and validation arity are both
derived, so they cannot drift apart), query
validation, the result-plist shape, and the shared window predicate;
=dorg-ql-model.el= is the model-list adapter and the baseline matcher;
=dorg-ql-plain.el= is the plain-org adapter, whose timestamp predicates
reuse ~dorg-parse-section-items-at-heading~ plus the model matcher so they
cannot drift from the parser; and =dorg-ql-dolt.el= is the Dolt SQL
adapter.

* =dorg-ql-ast.el=

Normalized v2 AST and Lisp reader for ~dorg-ql~: the single public
parsing layer that lowers both the historical atomic forms (kept as
compatibility aliases) and the composable reader forms into one
backend-neutral AST.

| Symbol              | Description                                              |

* Materialized views and rendering

The public materialization lifecycle spans three modules; each symbol
below names its defining module.

| Symbol                  | Defined in | Description                     |
|-------------------------+------------+---------------------------------|
| ~dorg-materialize~      | =dorg-mode.el= | Public buffer lifecycle: materialize whole/window views into a buffer |
| ~dorg-materialized-view-scope~ | =dorg-projection.el= | Return nil, =whole=, or =partial= for a buffer |
| ~dorg-render~           | =dorg-render.el= | Render dorg repo as org-mode string |
| ~dorg-render-island~    | =dorg-render.el= | Render a node + subtree (with ancestor breadcrumb) as a string |
| ~dorg-render-subtree-ids~ | =dorg-render.el= | Recursive-CTE island primitive: a node's id plus all descendant ids |

~dorg-materialize~ is the only public operation that mutates a buffer into
a DOrg-backed view.  Both positional-buffer and keyword-first forms are
supported:

#+begin_src emacs-lisp
(dorg-materialize destination
                  :source registered-source
                  :revision exact-token
                  :window '(:focus
                            (101
                             (:extern :key "BEAD_ID" :value "tracker-cli-abc"))))

;; Defaults destination to the current buffer.
(dorg-materialize :source registered-source :revision exact-token)
#+end_src

~:source~ is a registered buffer that supplies the Dolt store and root;
the destination may be a fresh, unregistered buffer.  A supplied
~:revision~ is used for every load and label without rereading HEAD; nil
captures HEAD once.  ~:window~ is either nil for the whole root or exactly
~(:focus FOCI)~ for a bounded view.  Each focus is either a positive numeric
heading id or the canonical public external identity
~(:extern :key K :value V)~.  DOrg resolves external identities root-scoped
against the same exact revision used for rendering; zero matches and ambiguous
matches fail before mutation.  This lets a property-identified consumer pass
its durable domain identity without a numeric-id SQL prequery.  DOrg validates
the source, revision, root, and every focus before touching the destination.

The returned descriptor and private projection-view context retain the
canonical public focus identities.  The private renderer and durable
=#+DORG_WINDOW:= marker use only their resolved numeric ids, so restoration
does not expose a second consumer-facing identity representation.

Success returns ~(:scope SCOPE :revision TOKEN :root-id ROOT :window WINDOW :buffer BUFFER)~.
Whole and bounded materialization publish only exact bytes
plus neutral projection-view context.  Bounded views install =partial= scope.
Bytes and projection context publish atomically: a post-replacement error
restores both.

Zero/one-argument Dolt calls capture HEAD once and use the same exact whole-view
materializer; plain-org calls retain ordinary file reload behavior.
Revision/window lifecycle keywords require a Dolt-backed source.
~dorg-materialized-view-scope~ reads an explicit buffer and returns only nil,
=whole=, or =partial=; it never exposes the private lifecycle context.

There is no background external-change polling.  Use
~dorg-refresh-materialized-view~ (bound to =C-c C-x s=) to capture current HEAD,
or pass an exact public revision token.  Typed writes refresh at the exact token
returned by their commit.

~dorg-render~ and ~dorg-render-island~ are retained pure string readers.
They do not mutate buffers or publish lifecycle state.

** Public low-level model readers

These Dolt readers are public low-level APIs, implemented in
=dorg-model-load.el=.  Prefer the query/render facades for selection and
rendered views; use these readers when typed heading/item models are needed.
Both return a hash table from numeric heading ID to ~dorg-heading~, with
items populated as model objects.

| Symbol | Arguments | Scope |
|--------+-----------+-------|
| ~dorg-model-load-headings~ | ~(dolt-dir root-id ids &optional as-of headline-only query-fn levels)~ | Explicit IDs within the root, or the whole root when ~ids~ is nil. |
| ~dorg-model-load-tree~ | ~(dolt-dir root-id &optional as-of)~ | Explicit whole-root convenience; delegates to ~dorg-model-load-headings~ with nil IDs. |

*Nil IDs mean the whole root, not an empty selection.*  Consumers hydrating
query results must short-circuit an empty ID list before calling the loader.
For example, this preserves the hash-table result shape and performs no
loader SQL for an empty selection:

#+begin_src emacs-lisp
(if ids
    (dorg-model-load-headings dolt-dir root-id ids revision)
  (make-hash-table :test #'eql))
#+end_src

by the query.  Pass that same commit as ~as-of~; omitting it reads current
state and does not preserve the query snapshot.  ~headline-only~ skips
item/body/drawer/planning payloads and leaves each heading's items nil, for
example when loading breadcrumb ancestors.

** User-facing management commands

These discoverable commands manage DOrg-managed sql-servers without
evaluating the lower-level lifecycle APIs above.  A server is
"DOrg-managed" only when DOrg holds an ownership claim for it (see
[[file:configuration.org][configuration.org]]); a manual external =dolt
sql-server= with no DOrg claim is not listed or touched.

| Symbol                  | Description                                          |
|-------------------------+------------------------------------------------------|
| ~dorg-dolt-server-list~      | Structured inventory (plists) of managed servers/claims |
| ~dorg-dolt-list~     | Show that inventory in a =*DOrg Servers*= buffer        |
| ~dorg-dolt-start~     | Ensure a server for a repo (defaults to current buffer) |
| ~dorg-dolt-stop~      | Owner-safe stop/detach for a repo                       |
| ~dorg-dolt-stop-all~ | Stop every server this Emacs process owns               |

~dorg-dolt-server-list~ returns one plist per known server with keys
=:dolt-dir :port :owner-pid :server-pid :host :policy :protocol
:created-at :last-used :role :status=.  ~:role~ is one of =owned=
(this Emacs runs/holds the claim), =attached= (this Emacs is a client
of a foreign owner), or =foreign= (another DOrg process owns it).
~:status~ classifies the claim as =live=, =dead=, =stale=,
=unreachable=, or =incompatible=.

Cross-process inventory uses a stable, non-authoritative per-user index of
canonical store paths.  Ownership and status remain authoritative only in each
store's =<store>/.dorg/server.claim=.  This makes a detached server started by
one CLI process visible to a later ~dorg dolt list~ process without scanning
arbitrary OS processes or moving ownership out of the store.

~dorg-dolt-stop~ is owner-safe: it stops a server this Emacs owns
and releases that claim (token-checked), detaches an attach-only
client while leaving the owner's claim intact, and *refuses* (with the
owner pid/port) to stop a live server owned by another DOrg process.
~dorg-dolt-start~ is an explicit user action and always ensures a durable
detached daemon.  Ordinary strict =server= SQL reuses any visible
compatible managed server regardless of policy; when none is visible, it
consults ~dorg-dolt-server-autostart~ (default =nil=, see
[[file:configuration.org][configuration.org]]): disabled attaches only an
already-live server and otherwise errors naming ~dorg dolt start~ as the
remedy, enabled autostarts the same detached daemon lifecycle as
~dorg-dolt-start~.  Every path a daemon is started on is stopped manually
with ~dorg-dolt-stop~ / ~dorg dolt stop~.

The =bin/dorg= CLI exposes this same surface noninteractively as the
=dolt= command family — ~dorg dolt list~ / =status= (over
~dorg-dolt-server-list~), ~dorg dolt start~ / =ensure= (over
~dorg-dolt-start~), ~dorg dolt stop~ (over ~dorg-dolt-stop~), and
~dorg dolt stop-all~ (over ~dorg-dolt-stop-all~) — with the identical
ownership and safety semantics and no minibuffer prompts.  See
[[file:cli.org][docs/cli.org]].

=dorg-id.el= owns two concerns: snowflake id *generation* and DORG_ID

* =dorg-ext-rebuild.el=

| Symbol | Description |
|--------+-------------|
| ~dorg-ext-rebuild-index~ | Audit or atomically repair one declared extension index scope at an exact Dolt revision |
| ~dorg-ext-rebuild-audit-store~ | Read-only whole-store ownership audit of every declared derived row at an exact Dolt revision |
| ~dorg-ext-rebuild-plan-policy-upgrade~ | Read-only plan of an explicit OLD-to-NEW derived-policy transition frozen at a revision |
| ~dorg-ext-rebuild-apply-policy-upgrade~ | Re-derive and atomically apply one policy-upgrade plan, returning a self-contained receipt |
| ~dorg-ext-rebuild-invert-policy-upgrade~ | Exactly restore the pre-upgrade derived rows from a successful forward receipt |

This Dolt-only administrative entry point takes an extension, root id,
=:dolt-dir=, =:revision=, and =:mode= (=audit= or =repair=).  It uses the
registered projector rather than accepting rows or SQL.  See
[[file:backend-extension.org][backend-extension.org]] for its full-snapshot
context and scope-column contract.

=dorg-ext-rebuild-audit-store= takes an extension plus =:dolt-dir=,
=:revision= and =:identity=; it has no root argument and no repair mode.  At
the supplied committed revision it returns a read-only ownership census for
every declared derived table.  Its =:tables= entries retain full row alists and
multiplicity, classifying every observed row as canonical-root owned,
stored-only-root owned, orphan, ambiguous, or undeclared scope.  =:clean= is
only an ownership-census result, not a projected-value correctness claim.
Callers must treat =:complete nil= (with =:errors=) as non-clean and must not
infer a zero count for an unread table.

The three policy-upgrade functions are a deliberate migration of derivation
policy, not ordinary repair: plan takes a closed request with content-addressed
OLD and NEW producer identities resolved through the extension's
=:producer-resolver=, apply accepts only a plan and re-derives it before
writing, and invert accepts only the forward receipt and restores the exact
pre-upgrade derived rows.  See
[[file:backend-extension.org::*Explicit derived-policy upgrade and exact inverse][backend-extension.org]]
for the classification, receipt and reconciliation contract.

* Managed clock lifecycle

Require =dorg-clock= to use the persisted clock API; the Org UI adapter is a
separate opt-in package.  Clocks have one named Dolt authority and scope.  A
plain-Org file can identify a task, but cannot own the clock ledger.

| Entry point | Contract |
|-------------+----------|
| ~dorg-api-make-owner-intent FAMILY REQUEST &rest OPTIONS~ | Construct an immutable request for a registered metadata family; clock callers use ~dorg-clock-make-intent~. |
| ~dorg-clock-make-intent ACTION &rest ARGUMENTS~ | Construct an immutable =start=, =stop=, =switch=, =correct=, =cancel= or =adopt= request. |
| ~dorg-api-execute INTENT :mode MODE~ | Validate/preview (=dry-run=) or persist (=apply=) through the metadata owner; no execution-time source, scope, time or task override. |
| ~dorg-clock-read SCOPE-ID &rest OPTIONS~ | Read the scope and intervals from =:source=, at a required =:observed-at= UTC instant and optional =:snapshot=; never start/stop a clock or create task identity. |
| ~dorg-clock-render-interval START-UTC END-UTC ZONE~ | Render a completed interval as an Org CLOCK line; UTC seconds remain authoritative. |

Requests carry an explicit source, base, operation ID, scope/interval IDs,
expected active interval, integer UTC epoch seconds and IANA time zone.
Action-specific fields include the canonical task reference, correction or
adoption data.  The owner enforces active-interval consistency and validates
records before committing.  A lost response must retain the exact immutable
request for reconciliation/retry; creating a fresh operation ID could create a
second operation.  Generic property edits cannot bypass this protocol.

The =DORG_CLOCK_= properties are canonical data; Org CLOCK text is a derived
projection.  Adopting a legacy line is explicit and pins its task, source
revision and raw bytes.  Ambiguous wall times and indistinguishable duplicate
lines are refused, rather than guessed.  See
[[file:configuration.org::*Managed clocks (opt-in Emacs)][the optional Emacs adapter]]
for local indicators, dirty-buffer deferral and the differences from stock Org
clock hooks and idle handling.

* Managed clock task references

~dorg-clock-task-ref SOURCE HEADING-ID~ returns a typed value with =:kind=,
=:heading-id= and =:canonical=.  A Dolt task also has =:store-id= and
=:root-id=; its canonical form is
=dolt:v1:<32-lowercase-hex-store-id>:<root-id>:<heading-id>=.  A plain task
has =:root-identity=, read from the file's =#+DORG_STORE_ID:= root keyword;
its form is =plain:v1:<base64-root-identity>:<heading-id>=.  Both heading IDs
are stable =DORG_ID= values.  ~dorg-clock-task-ref-decode CANONICAL~ returns
the same typed value, or nil for a malformed string.  Paths locate sources but
are never compared as identity.  Copies of one Dolt store preserve its ID;
=:fork= deliberately changes it.

New Dolt stores receive a random 128-bit =store-id= row in =dorg_meta= during
~dorg-init~.  ~dorg-api-identify-store DOLT-DIR~ identifies an older store
once, refusing an existing ID.  Passing =:fork t= replaces the ID and records
the prior value under =store-id:prior:<new-id>= in the same commit.  This door
requires a clean Dolt working set so it cannot commit unrelated pending changes.  The CLI
exposes this as =dorg dolt identify DIR [--fork]=.  An unidentified Dolt store
or plain root returns =(:kind unresolved :reason store-unidentified ...)=
without a canonical string; clocking that task is refused.  Clock reads and
task-reference encoding never create identity.  For a plain file, its author or
importer writes =#+DORG_STORE_ID:= directly in the file; typed DOrg mutation
continues to refuse writes to every =DORG_*= keyword.  Changing unrelated plain-file
bytes leaves its task reference unchanged.  Adoption separately pins the exact
source revision and raw CLOCK occurrence.  A claim on an adopted line uses its
task reference, heading ID and raw CLOCK bytes; moving the line to a different
occurrence cannot adopt it twice.  Byte-identical CLOCK lines in one heading
are ambiguous and must be resolved in the source before adoption.
