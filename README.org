#+title: DOrg
#+subtitle: Query and update Org data from Emacs, scripts and agents
#+author: Octavian Cosmin

*DOrg* gives Emacs, scripts and agents a structured API for Org data.  Query
headings, properties, planning and text; preview a change, then apply it.
The same query and mutation languages work with ordinary Org files and
[[https://www.dolthub.com/][Dolt]], a versioned SQL database.

With Dolt, changes become commits you can inspect and revisit.  Emacs shows
the data as an Org document, while applications share the underlying store.

The video below compresses a day of agent work at the Recursive Agents
Hackathon into 30 seconds: claims, handoffs, reviews and completed tasks.
[[https://github.com/cosmicz/embead][Embead]] supplies the task workflow; DOrg and Dolt preserve its state and history.

https://github.com/user-attachments/assets/4fd6b887-d325-40b0-bfd9-417ef65697ac

Choose where your data lives:

| Backend   | Source of truth | Editing model                                      |
|-----------+-----------------+----------------------------------------------------|
| Plain Org | The file        | Edit normally in Emacs or use DOrg's surgical edits. |
| Dolt      | The database    | Apply typed changes; view the result as Org.         |

Plain-file edits preserve untouched bytes and check that the source has not
changed.  Saved applies serialize participating DOrg writers; other editors
do not participate in that lock.  Dolt adds transactional commits, exact
revision reads and durable receipts for supplied operation IDs.  Its Org
buffers are read-only views.

Choose Dolt when multiple writers, history and committed snapshots matter.
DOrg owns storage and structure; applications own their workflow and policies.

This is *v0.2.0*.  See [[file:CHANGELOG.org][the changelog]] for changes since the
published v0.1.0 release and [[*Upgrading][Upgrading]] before opening an older store.

* Install

Use GNU Emacs *30.1*, the tested and supported runtime.  Plain Org needs no
Dolt binary.  For database-backed files, install *Dolt 1.86.4 or newer* on
=PATH=.  The MySQL wire client and CLI dependencies are bundled; keep =lib/=
with the sources.

From a checkout:

#+begin_src sh
make install
export PATH="$HOME/bin:$PATH"
dorg doctor --install
#+end_src

The defaults install a self-contained, byte-compiled runtime in =~/.local/share/dorg=
and link =~/bin/dorg= to its launcher.  It does not depend on the checkout or
compile into it.  Override =PREFIX=, =BINDIR= or =DORG_HOME= as needed; the
Emacs used to compile must be the one the launcher runs.  See
[[file:docs/configuration.org::*Runtime installation][installation details]].

For interactive Emacs, add that installed tree (or a development checkout):

#+begin_src emacs-lisp
(add-to-list 'load-path (expand-file-name "~/.local/share/dorg"))
(require 'dorg)
#+end_src

When upgrading from an older =make install=, the old =~/share/dorg= stays in
place and =~/bin/dorg= points at the new runtime.  Update any Emacs =load-path=
entry for the old tree; you may remove that tree by hand after checking it.
An older =install.sh= may have cloned its source into =~/.local/share/dorg=.
The new install refuses to replace that unowned checkout.  Move it to
=~/.local/src/dorg= yourself, or choose another runtime with =PREFIX= or
=DORG_HOME=.  The installer does not move either tree automatically.

* What you can build

- *Query Org structure:* filter headings, traverse trees, select columns and
  match text with explicit case sensitivity.  Snapshot responses include the
  source revision.  [[file:docs/query.org][Query language]]
- *Preview and apply edits:* change heading fields, properties, planning and
  content, or capture and move headings.  Dry-run reports the planned changes
  and whether the backend supports them.  [[file:docs/mutate.org][Mutation language]]
- *Rank search results:* opt-in BM25 indexes heading titles and their directly
  owned text in Dolt.  Choose case-sensitive or insensitive search and a
  result limit.  Descendant text and metadata are excluded.
  [[file:docs/query.org][Search and measurements]]
- *Track time:* persist clock starts, stops, switches and corrections using
  UTC instants and an IANA time zone.  A Dolt store owns the clock records;
  tasks can live in Dolt or identified plain files.  An optional Emacs adapter
  keeps local clock indicators in sync.  [[file:docs/configuration.org::*Managed clocks (opt-in Emacs)][Clock setup]]
- *Browse history:* render Org views at an exact revision, inspect earlier
  states and explicitly restore data.
  [[file:docs/api.org::*Materialized views and rendering][View API]]
- *Build applications:* add derived indexes and domain-specific behavior
  through extensions.  Elisp, CLI and authenticated HTTP expose the shared
  query and mutation APIs.  [[file:docs/backend-extension.org][Extension contracts]]

** Example: an agent work tracker

[[https://github.com/cosmicz/embead][Embead]] layers bead identity, workflow, assignment and review on top of
DOrg.  A task can be assigned, revised and accepted while keeping the document
queryable and its changes in Dolt history.  Embead owns the task semantics;
DOrg owns the structural data and commits.  Git continues to own source code.

The hackathon recording above follows 96 tasks across 1,615 Dolt commits.
It shows assignments, reviews and completed work as changes to the same
structured data that Emacs can display and programs can query.

* Try a complete workflow
:PROPERTIES:
:header-args:bash: :session *dorg-readme* :results output verbatim :exports both :eval never-export :wrap example text
:END:

The following example uses a disposable Dolt store, Bash and =jq=.  It imports
two headings, queries one, previews a property change, applies it against the
queried revision, then renders the resulting Org document and reads history.
No existing task file is involved.

Run the blocks in order with =C-c C-c= after enabling shell Babel with
=(require 'ob-shell')=, or copy the commands into one Bash shell.  Babel keeps
their variables in the shared =*dorg-readme*= session.  The results below are
saved output from an actual run; exporting this document does not rerun it.
Your heading IDs and commit hashes will differ.

** Import and query

#+name: readme-demo-bootstrap
#+begin_src bash :exports both
set -euo pipefail

export DORG_EXAMPLE=$(mktemp -d "${TMPDIR:-/tmp}/dorg-example.XXXXXX")

cat > "$DORG_EXAMPLE/tasks.org" <<'EOF'
,* TODO Try DOrg :work:
,* TODO Write a note :home:
EOF

dorg import -f "$DORG_EXAMPLE/tasks.org" \
  --dolt-dir "$DORG_EXAMPLE/store" \
  --target-file "$DORG_EXAMPLE/tasks.org" --mode bootstrap --json \
  > "$DORG_EXAMPLE/import.json"

dorg dolt start "$DORG_EXAMPLE/store" > "$DORG_EXAMPLE/server-start.log"

dorg query '(tag "work")' -f "$DORG_EXAMPLE/tasks.org" \
  --dolt-dir "$DORG_EXAMPLE/store"

id=$(dorg query '(title "Try DOrg")' -f "$DORG_EXAMPLE/tasks.org" \
  --dolt-dir "$DORG_EXAMPLE/store" | cut -f1)
test -n "$id"
#+end_src

#+RESULTS: readme-demo-bootstrap
#+begin_example text
107400172245880833	Try DOrg
#+end_example

Import allocates stable heading IDs and commits the document.  It does not
rewrite the source file; materialization below renders an in-memory view.
The query reads the bound database.  Its text output is an ID and title,
separated by a tab.  Capture the actual ID instead of copying one from a demo.
Explicit =dorg dolt start= keeps a managed server available across CLI calls;
normal batch reads require a running server.

** Preview, then apply

#+name: readme-demo-preview
#+begin_src bash :exports both :wrap example json
dorg query '(title "Try DOrg")' -f "$DORG_EXAMPLE/tasks.org" \
  --dolt-dir "$DORG_EXAMPLE/store" --json > "$DORG_EXAMPLE/query.json"

base=$(jq -er '.data.snapshot.head' "$DORG_EXAMPLE/query.json")
form="(on (id $id) (set (property \"STATUS\") \"reviewed\"))"

dorg mutate "$form" --dry-run --base "$base" -f "$DORG_EXAMPLE/tasks.org" \
  --dolt-dir "$DORG_EXAMPLE/store" --json > "$DORG_EXAMPLE/plan.json"

jq '.data | {supported, patches}' "$DORG_EXAMPLE/plan.json"
#+end_src

#+RESULTS: readme-demo-preview
#+begin_example json
{
  "supported": true,
  "patches": [
    "(:op put :target (:property :host (:heading :id 107400172245880833) :name \"STATUS\") :value \"reviewed\")"
  ]
}
#+end_example

Read the preview before running the apply block:

#+name: readme-demo-apply
#+begin_src bash :exports both
dorg mutate "$form" --apply --base "$base" -f "$DORG_EXAMPLE/tasks.org" \
  --dolt-dir "$DORG_EXAMPLE/store" --json > "$DORG_EXAMPLE/apply.json"

dorg query '(property "STATUS" "reviewed")' -f "$DORG_EXAMPLE/tasks.org" \
  --dolt-dir "$DORG_EXAMPLE/store"
#+end_src

#+RESULTS: readme-demo-apply
#+begin_example text
107400172245880833	Try DOrg
#+end_example

Capture the base from the query snapshot:
the current CLI dry-run omits the Elisp response's =:base=, and its
=base-commit= field can be null.  =--base= refuses apply if the source changed;
re-read and review a new plan rather than removing the guard.  Query-scoped
writes additionally require =--expect-targets= with the exact dry-run target
set.  No command defaults to apply.  JSON uses the =ok/data/error= envelope;
IDs can exceed JavaScript's exact integer range, so preserve them losslessly.

** Inspect the Org view and history

The public Elisp API supplies exact materialization and history; there is no
CLI history verb.  Run this in the same shell (adjust the runtime path if you
installed elsewhere by setting =DORG_RUNTIME=):

#+name: readme-demo-view
#+begin_src bash :exports both :wrap example org
printf 'Materialized Org:\n'
emacs --batch -Q -L "${DORG_RUNTIME:-$HOME/.local/share/dorg}" -l dorg -l dorg-history --eval '
(let* ((dir (getenv "DORG_EXAMPLE"))
       (file (expand-file-name "tasks.org" dir))
       (store (expand-file-name "store" dir))
       (receipt (with-temp-buffer
                  (insert-file-contents (expand-file-name "apply.json" dir))
                  (json-parse-buffer :object-type (quote plist))))
       (revision (plist-get (plist-get receipt :data) :new-token))
       (buffer (find-file-noselect file)))
  (dorg-bind-existing-dolt file store)
  (dorg-materialize buffer :source buffer :revision revision)
  (with-current-buffer buffer (princ (buffer-string)))
  (princ (format "\nHistory entries: %d\n"
                 (length (dorg-history-commits
                          store (dorg-repo-root-id store file))))))' \
  | sed -e '/^#+DORG_DOLT_DIR:/d' -e 's/^#+DORG_HASH:/Revision:/'
#+end_src

#+RESULTS: readme-demo-view
#+begin_example org
Materialized Org:
Revision: hvg19sn6vbhpblca2kjtpnrlpeoa7tkg
,* TODO Try DOrg  :work:
:PROPERTIES:
:DORG_ID: 107400172245880833
:STATUS: reviewed
:END:
,* TODO Write a note  :home:
:PROPERTIES:
:DORG_ID: 107400172245880834
:END:

History entries: 4
#+end_example

The view contains the same heading ID and =:STATUS: reviewed=, plus the exact
Dolt revision.  The display labels the revision and omits the local
store-directory header; the heading content is unchanged.

The batch view is in memory; =tasks.org= on disk remains the import input.
For an interactive view, open that path in Emacs, run =M-x dorg-bind-dolt=
with this example's store, then =M-x dorg-refresh-materialized-view=.
The bound buffer is a read-only projection.  =M-x dorg-history= opens the
history browser; subsequent explicit refreshes follow current HEAD.
Historical viewing does not restore old data; restore is a separate mutation.

When finished, stop only this example's server:

#+name: readme-demo-stop
#+begin_src bash :exports both
dorg dolt stop "$DORG_EXAMPLE/store" > "$DORG_EXAMPLE/server-stop.log"
printf 'Example server stopped.\n'
#+end_src

#+RESULTS: readme-demo-stop
#+begin_example text
Example server stopped.
#+end_example

The example directory is retained for inspection; remove it when no longer
needed.  Keep independent backups before trying administrative import on
important data.  In Emacs, =M-x dorg-setup= offers the equivalent first-import,
bind and projection setup for a disposable file.

* Limits and operations

There is no universal latency bound.  Scoped reads and changed-document index
maintenance avoid unnecessary work; cold startup, import and whole-root
rendering still have different costs.  The query reference gives the workload
and revision for its measurements.

Plain-file and Dolt persistence guarantees differ, even when a mutation form
is shared.  DOrg's local plain writer lock covers saved DOrg applies, not
arbitrary editors, remote files or multi-link aliases.  Plain operation IDs
are echoed; durable retry reconciliation requires Dolt.  See
[[file:docs/mutate.org][the supported operations and refusal contracts]].

Recurring-calendar expansion and the new Embead replay dashboard are not
shipped features of this release.  Managed clocks do not replace all stock
Org clock hooks or idle behavior.  Required capabilities should be checked at
the public API boundary rather than assumed from the storage backend.

Use =dorg doctor -f tasks.org= to report consistency findings; =--fix= applies
only its supported repairs and rechecks.  Preserve the error and source
revision when reporting a failure.  Making a Dolt projection writable is not a
repair.  Server commands and failure diagnostics are in
[[file:docs/configuration.org][the operations reference]].

** Emacs 28 and 29 compatibility

Emacs 28 and 29 are unsupported and unverified, not explicitly blocked by
package metadata.  Linux CI on 29.1 and 29.4 stopped at an =ert-skip= instead
of completing the suite.  That is a test-runner limitation, not proof that
every DOrg operation fails on 29.  Use the supported Emacs 30.1 target.

* Upgrading

DOrg v0.1.0 used schema 6; current source uses schema 8.  Explicit
=dorg-migrate-schema= steps take 6→7→8.  Ordinary opening never migrates an
existing store.  Load its required extensions, use a DOrg-managed server and
coordinate writers before the operator migration.  Pre-v6 development stores
have no supported upgrade path; recreate those from recoverable Org source.
[[file:docs/configuration.org::*Portable file bindings and schema migration][Migration procedure]]

Existing stores also need explicit =dorg dolt identify DIR= before their tasks
can be used by managed clocks.  Until then, task references report
=store-unidentified= and clock-in refuses.  Plain task files need an author-set
=#+DORG_STORE_ID:= root keyword and stable heading =DORG_ID= values; the generic
mutation API deliberately refuses writes to =DORG_= keywords.

The retired sequence mutation spellings are hard errors.  Follow the
[[file:CHANGELOG.org::*Mutation addressing migration][changelog migration table]] when advancing a consumer's DOrg pin;
there is no grammar-version switch or compatibility alias.  Coordinate the
DOrg library, installed CLI and application pins that share a store.
